# Версионирование и changelog (все проекты владельца)

Источник этого документа — корень `dziominpavel.github.io`. Каждый проект
получает от корня свою копию (`docs/versioning.md`); дети не знают о других
проектах владельца. Перечень проектов и трек каждого — `versioning.yaml`
корня; этого файла у детей нет.

## Модель: версия = релиз

`version` — это база **последнего опубликованного релиза**
(git-тег `vX.Y.Z`, ассеты в GitHub Releases). Между релизами файл `version`
НЕ трогается: всё новое копится в секции `## [Unreleased]` в `CHANGELOG.md`.

Промежуточных версий не существует: версия, не ставшая тегом, нигде не
появляется — ни в git, ни в релизе, ни на странице релизов владельца
(она читает только `releases/latest`, поэтому показать может только
опубликованный релиз).

Единственное место, где меняется файл `version`, — release-скрипт.
Бамп вне релиза запрещён.

### Обычная сессия (без релиза)

1. Начало сессии: прочитать `version` + верх `CHANGELOG.md` (должен быть
   `## [Unreleased]`).
2. Конец сессии / коммит / архивация change:
   `git status --porcelain` + `git diff --stat`.
   - есть **глобальная доработка** — новая функция, заметное изменение
     поведения, фикс, который пользователь реально видит (плюс доки о ней) →
     добавить пункт в `## [Unreleased]`;
   - **мелочь** — косметика UI (отступы, цвета, выравнивание, подпись
     элемента), локальные правки без заметного эффекта, а также одни только
     доки/спеки/тесты/чистый рефактор/CI → в `CHANGELOG` ничего не писать;
   - **файл `version` не менять**, версионные секции не создавать.

Пункт в `[Unreleased]` — часть работы над изменением, а не подготовка к
релизу. Откладывать запись до релиза нельзя: к релизу накопление и есть
источник классификации.

### Релиз (две фазы)

Ассеты и отображаемая версия запекаются **при сборке**, поэтому бамп
делается до неё. Release-скрипт разбит на две фазы; перепутать порядок
нельзя — любая фаза откажется работать.

**Фаза 1 — подготовка, до сборки:**

```powershell
release.ps1 -Prepare
```

1. Отказ, если `[Unreleased]` пуст (нечего готовить), если в нём нет
   пользовательского блока в формате контракта — жирных меток и буллетов
   выше первой строки `###`, — или рабочее дерево нечистое (сначала
   закоммичь работу). Отказ печатает текст блока: это увидят пользователи.
2. Классифицировать **всё** накопленное по наивысшему уровню:
   - **MAJOR (`X.0.0`)** — ломающее совместимость: миграция с потерей
     данных, смена схемы формата, смена `minSdk`/архитектуры, удаление
     фичи (пометка `**BREAKING:**` или ключ `-Major`).
   - **MINOR (`x.Y.0`)** — новая видимая фича или поведение
     (`### Добавлено`, `### Изменено`).
   - **PATCH (`x.y.Z`)** — в накопленном только фиксы (`### Исправлено`).
3. Записать новую базу в `version`, свернуть `[Unreleased]` в
   `## [x.y.z] — дата (УРОВЕНЬ)`.

Тег, коммит и релиз на этом этапе **не создаются** — только два изменённых
файла. Если сборка не удалась: `git checkout -- version CHANGELOG.md`.

**Фаза 2 — публикация, после сборки (`dist/` заполнен):**

```powershell
release.ps1
```

4. Отказ, если `[Unreleased]` непуст (подготовка не выполнена), если
   дерево нечисто кроме `version`/`CHANGELOG.md`, если версия и верх
   changelog разошлись.
5. Коммит файлов бампа → контроль, что в `HEAD` есть секция новой
   версии → тег `vX.Y.Z` → push → публикация релиза: заметки из секции
   changelog + ассеты.

У проектов со своим билд-скриптом подготовка вызывается автоматически
первым шагом самого билда — отдельно `-Prepare` там не запускают.
У остальных владелец выполняет фазы подряд: `-Prepare` → сборка и копия
в `dist/` → `release.ps1`.

Несколько независимых изменений между релизами образуют **одну** версию.
Отдельная версия на каждое изменение запрещена.

## Формат CHANGELOG.md

```markdown
## [Unreleased]

**Добавлено**
- Что заметно пользователю: одна строка = одно изменение.
- Ещё одно изменение одной строкой.

**Исправлено**
- Что было сломано и как это выглядит теперь.

### Добавлено
- Описание фичи: change-id, состав изменений, тесты.

### Исправлено
- Что меняется технически.

## [1.6.0] — 2026-10-03 (MINOR)

**Добавлено**
- Что заметно пользователю в этой версии.

### Добавлено
- ...
```

Правила:

- секция `## [Unreleased]` всегда сверху, без номера версии;
- ниже — выпущенные версии `## [X.Y.Z] — дата (УРОВЕНЬ)`, новые сверху;
- каждая секция начинается с **пользовательского блока** (саммари),
  идущего **выше первой строки** `###`. Формат блока: жирные метки
  категорий (`**Добавлено**`, `**Исправлено**`, `**Изменено**` — метка,
  а не `###`: первая же `###`-строка обрывает блок) и буллеты. Правила
  блока: одна строка = одно изменение, строка ≤140 символов, без `` ` ``
  и без инженерных маркеров (change-id, имена файлов, тесты, метрики —
  всё это уходит под `###`). Блок писать **в момент работы**, вместе
  с пунктами категорий, а не готовить отдельно перед релизом. Под
  категориями `###` идут инженерские детали;
- язык — русский, адресат — пользователь проекта;
- категории: `### Добавлено` (MINOR), `### Исправлено` (PATCH),
  `### Изменено` (перемещения, смена поведения; ломающее — пометка
  `**BREAKING:**`);
- в changelog попадают **только глобальные доработки** — то, что пользователь
  заметит в новой версии: новая функция, смена поведения, заметный фикс.
  Мелочь в changelog не пишется: косметика UI (отступы, цвета, выравнивание,
  подпись элемента) и локальные правки без заметного эффекта — это не
  журнал коммитов;
- в changelog не попадают чистые доки, спеки, тесты, CI и внутренний
  рефактор без пользовательского эффекта.

### Заметки GitHub-Release

Тело релиза на GitHub берётся из changelog — отдельный текст не пишется:

- заметки = блок версионной секции **до первой строки `###`** — ровно
  те жирные метки и буллеты, что видит пользователь;
- если строк `###` в секции нет (исторические секции, сложившиеся до
  внедрения release-скрипта), заметками становится вся секция целиком —
  их не чинят задним числом;
- блок вне формата (связная проза, `` ` `` в тексте, строка длиннее
  140 символов, ни одного буллета) — ошибка: подготовка релиза откажет
  и напечатает текст блока с пометкой «это увидят пользователи»;
- текст доходит до GitHub без перекодировки (UTF-8 без BOM): кириллица,
  эм-даш и символы вроде `≥` в релизе не искажаются.

Так одна запись работает и как история проекта, и как описание релиза:
дублировать её отдельным «релизным описанием» нельзя.

## Два трека

| | Релизный | Статический |
|---|---|---|
| Версия растёт | только на релизе | заморожена |
| Git-теги, GitHub Releases | да | нет |
| Файл `version` | обязателен | нет (или строка в манифесте, не меняется) |
| `CHANGELOG.md` | обязателен | обязателен |

К какому треку относится конкретный проект — в `versioning.yaml` корня.
**В этот документ списки проектов намеренно не вынесены:** он копируется
в каждый дочерний проект, а тот не должен знать чужих репозиториев,
их треков и версий. У дочернего проекта на руках только собственные
`CHANGELOG.md`, файл версии, `docs/versioning.md` и `check-version.py`.

У статического трека между релизами тоже есть `[Unreleased]`: changelog
ведётся, а версия не двигается и тег не ставится.

У релизного проекта, у которого нет release-конвейера (нет артефактов
и публикации), бамп делается по явной команде владельца «выпусти версию»
с тем же порядком: классификация `[Unreleased]`, запись в файл версии,
сворачивание секции, `check-version.py`.

## Android: версия отделена от счётчика сборок

- `versionName` берётся из файла `version` и не зависит от сборки.
- `versionCode` = база + `git rev-list --count HEAD` — растёт монотонно на
  каждый коммит, чтобы обновление всегда устанавливалось.
- Автобамп номера при каждой `assemble`/`install`/`bundle` запрещён;
  `version.properties` и счётчики сборок не используются.

## Автоматическая проверка

`scripts/check-version.py` сверяет формат файла `version` с верхней
версионной секцией `CHANGELOG.md` и проверяет верхний блок секции
`[Unreleased]` по формат-контракту (см. «Заметки GitHub-Release»): каждая
непустая строка блока — жирная метка категории или буллет, в блоке ≥1
буллет, строка ≤140 символов, символ `` ` `` запрещён, секция с пунктами не
начинается с `###`.

```bash
python scripts/check-version.py      # exit 0 — согласовано
                                    # exit 1 — рассинхрон, ошибка формата
                                    #          или нарушение блока
```

Блок проверяется во всех режимах (самопроверка, `--all`, `--project`) и для
проектов обоих треков. Что проверкой НЕ покрывается: пустая секция
`[Unreleased]` (это подсказка NO_BUMP, а не ошибка) и версионные секции,
включая исторические — контракт верхнего блока действует только для
`[Unreleased]`. Гейт `-Prepare` release-скрипта проверяет тот же блок ещё
раз в момент релиза.

Из корня проекта проверка идёт по своему файлу; полный обход всех проектов
делается только из корня владельца — у дочернего проекта такого списка нет.
Проверка обязательна перед тегом (её же выполняет release-скрипт).

## Первичное заполнение (бэкфилл)

Если у проекта ещё нет `CHANGELOG.md`:

1. `## [Unreleased]` — пустая секция сверху.
2. Одна сводная секция «История до введения changelog» — 5–15 пунктов по
   этапам `git log`, по-русски, про содержательные изменения, а не про
   коммиты.
3. По секции на каждый существующий тег (`git tag --sort=-v:refname`) —
   с датой и уровнем, если уровень определяется; иначе без уровня.
4. **Сборочные номера, не бывшие релизами, не перечислять.** У проектов со
   старыми счётчиками сборок (сотни и тысячи сборок) история складывается
   в одну сводную секцию, а не в сотни записей.

Заполнение — один раз вручную; генерация из git-истории не используется.

## Запреты

- Не писать в changelog мелочь: запись делается только для глобальной
  доработки, которую пользователь заметит. Правка UI «на пару пикселей»,
  подпись, отступ или цвет в `[Unreleased]` не попадает.
- Не бампить `version` вне релиза (бамп и есть релиз).
- Не держать версию в двух местах.
- Не выпускать версию «на всякий случай» и не публиковать релиз при пустом
  `[Unreleased]`.
- Не начинать секцию с `###` и не писать вместо блока связную прозу:
  без блока в формате контракта (жирные метки + буллеты, без `` ` ``)
  подготовка релиза откажет, а тело релиза осталось бы пустым.
- Не писать отдельное описание релиза помимо changelog: заметки на GitHub
  берутся из секции автоматически.
- Не считать версию из счётчика сборок, счёта коммитов или иного значения,
  меняющегося при каждой сборке.
- Не писать в `AGENTS.md` и файлы проекта знания о других проектах владельца:
  дети получают только свои файлы.
