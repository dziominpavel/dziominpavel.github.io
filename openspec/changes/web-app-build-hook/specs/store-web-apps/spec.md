# Spec Delta

## MODIFIED Requirements

### Requirement: Реестр веб-приложений

`registry.yaml` MUST содержать опциональную секцию `web:` — записи веб-приложений. Ключ записи MUST соответствовать паттерну `[a-z0-9-]` и служить слагом страницы веб-приложения (`/apps/<key>/`). Запись MUST указывать репозиторий-источник и метаданные карточки (название, описание; иконка опциональна). Источником статики MAY быть папка `web/`, либо запись MAY объявлять команду сборки `build`; для записи с `build` папка `web/` MUST NOT требоваться. Запись секции `web:` MUST NOT требовать GitHub Release, файла `version` и скриншотов. Добавление веб-приложения в стор MUST требовать только добавления одной записи в секцию `web:` без правок кода стора.

#### Scenario: Добавление третьего веб-приложения

- **WHEN** владелец добавляет новую запись в секцию `web:`
- **THEN** после ближайшей сборки появляются страница `/apps/<slug>/` и карточка на главной, код стора не изменялся

#### Scenario: Запись со сборкой из исходников

- **WHEN** владелец добавляет запись с полем `build`, а папки `web/` в репозитории-источнике нет
- **THEN** после ближайшей сборки появляется страница `/apps/<slug>/` из результата команды сборки, код стора не изменялся

#### Scenario: Некорректный ключ веб-записи

- **WHEN** ключ записи в секции `web:` не соответствует `[a-z0-9-]`
- **THEN** запись отклоняется с предупреждением в логе; остальные записи витрины обрабатываются

### Requirement: Публикация статики веб-приложений

Сборка витрины MUST получать статику каждой валидной записи `web:` — из папки `web/` источника либо из результата объявленной команды сборки — и публиковать её в `_site/apps/<slug>/`, чтобы страница открывалась по прямому URL и полностью работала без серверной части. Страница веб-приложения MUST содержать навигацию обратно в каталог. Язык страницы — только русский. Страница MUST работать без внешних CDN и сторонних хостингов (все ресурсы — с-origin витрины). Sitemap MUST включать страницы веб-приложений.

#### Scenario: Прямая ссылка на страницу

- **WHEN** посетитель открывает `/apps/<slug>/` по прямой ссылке
- **THEN** страница отдаётся, содержит ссылку обратно в каталог и включена в sitemap

#### Scenario: Страница собрана из исходников

- **WHEN** у записи объявлен `build` и команда оставила статику с `index.html`
- **THEN** страница публикуется из результата сборки, даже если папки `web/` в источнике нет

#### Scenario: Источник недоступен или битый

- **WHEN** статику получить не удалось (в источнике нет `index.html`, сборка статики не удалась или оставила пустой результат, ошибка получения репозитория)
- **THEN** сборка продолжается с предупреждением в логе, страница и карточка этого веб-приложения пропускаются, остальная витрина публикуется; сборка MUST NOT падать

### Requirement: Web-карточки на главной странице

Главная страница MUST показывать карточки веб-приложений в общей ленте вперемешку с карточками скачиваемых приложений по убыванию даты (без отдельной секции и отдельного заголовка): иконка (при отсутствии — буквенная заглушка), название, описание, дата обновления данных и primary-действие «Открыть в браузере» со ссылкой на `/apps/<slug>/`. Дата web-карточки с объявленным `data:` MUST браться из поля `updated` этого файла данных; дата web-карточки без `data:` MUST браться из даты последнего коммита, тронувшего источник статики: папку `web/`, а для записи с `build:` — репозиторий-источник; дата MUST NOT браться из даты сборки витрины, кроме fallback при недоступности коммит-даты. Макет web-карточки MUST быть консистентен с карточкой скачиваемого приложения. Карточка веб-приложения MUST NOT требовать версию, размер релиза и счётчик скачиваний.

#### Scenario: Два веб-приложения на витрине

- **WHEN** в секции `web:` две записи с разными датами обновления
- **THEN** в общей ленте каждая web-карточка стоит на позиции своей даты среди скачиваемых, каждая ведёт на свою страницу `/apps/<slug>/`

#### Scenario: Иконка веб-приложения отсутствует

- **WHEN** у записи нет файла иконки
- **THEN** карточка показывает буквенный плейсхолдер; сборка MUST NOT падать

#### Scenario: Дата web без данных — из коммита

- **WHEN** у web-записи нет поля `data:` и последний коммит папки `web/` источника датирован 28.09.2026
- **THEN** карточка показывает «Обновлено 28.09.2026», а не дату сборки витрины

#### Scenario: Дата карточки записи со сборкой

- **WHEN** у записи с `build` не объявлено `data:` и последний коммит репозитория-источника датирован 02.10.2026
- **THEN** карточка показывает «Обновлено 02.10.2026», а не дату сборки витрины

#### Scenario: Коммит-дата недоступна

- **WHEN** дату коммита источника статики получить не удалось (ошибка API, пустой ответ)
- **THEN** сборка продолжается с предупреждением в логе, карточка использует дату HEAD клона, а при его отсутствии — дату сборки; остальная витрина публикуется, сборка MUST NOT падать

### Requirement: Benchmark Web — статические результаты только на чтение

Страница `/apps/benchmark/` MUST отображать полный статический слепок консоли Benchmark, собираемый командой источника: ELO-рейтинг моделей, историю прогонов, аналитику, настройки, страницы моделей и дату обновления данных. Страница MUST работать только на чтение: элементы управления записью отображаются, но недоступны для использования, и никакие действия посетителя MUST NOT изменять данные. Данные обновляются только при сборке витрины.

#### Scenario: Открытие страницы рейтинга

- **WHEN** посетитель открывает `/apps/benchmark/`
- **THEN** он видит разделы консоли — рейтинг, историю, аналитику, настройки — и дату обновления
- **AND** элементы управления записью недоступны, данные изменить нельзя

#### Scenario: Обновились данные прогонов

- **WHEN** при сборке витрины `data/index.json` в репозитории Benchmark обновился
- **THEN** после ближайшего деплоя страница показывает обновлённые цифры без каких-либо действий посетителя

### Requirement: Оповещение витрины об обновлении web-статики

Репозиторий-источник веб-приложения, чья статика публикуется на витрине, MUST оповещать витрину (`repository_dispatch`) при пуше, тронувшем статику веб-приложения, её источник (для записи с `build:` — файлы, из которых собирается статика) либо файл данных (`data/**`), чтобы сборка витрины запускалась без ожидания расписания. Межрепозиторное оповещение MUST выполнять workflow самого репозитория-источника и MUST использовать секрет-токен, предоставляемый владельцем. При отсутствии секрета, его недействительности или ошибке отправки оповещение MUST пропускаться с предупреждением в логе, а пуш и публикация статики MUST NOT блокироваться; изменения в этом случае MUST подхватываться ближайшей сборкой витрины по расписанию. Оповещение MUST отправляться только по пуше, тронувшему статику, её источник или файл данных; пуш прочих файлов репозитория оповещение MUST NOT вызывать.

#### Scenario: Пуш статики веб-приложения

- **WHEN** владелец пушит коммит, тронувший `web/**` (для записи с `build:` — файлы сборки; для источника с файлом данных — также `data/**`), и репозиторий отправляет оповещение
- **THEN** витрина пересобирается по оповещению, не дожидаясь cron: страница `/apps/<slug>/` отдаёт новую статику, а дата web-карточки обновляется

#### Scenario: Секрет оповещения не настроен

- **WHEN** в репозитории-источнике отсутствует секрет-токен либо он недействителен
- **THEN** оповещение пропускается с предупреждением в логе, пуш проходит успешно, а изменение показывается на витрине после ближайшей сборки по расписанию

#### Scenario: Пуш файлов вне статики

- **WHEN** коммит не трогает ни статику (её источник), ни файл данных
- **THEN** оповещение витрины не отправляется и сборка витрины не запускается

#### Scenario: Релиз приложения, не трогающий статику

- **WHEN** в репозитории опубликован GitHub-Release скачиваемого приложения, а статика веб-приложения не менялась
- **THEN** оповещение о релизе отправляет release-скрипт (capability `app-release-pipeline`), а workflow репозитория-источника статики не срабатывает

## ADDED Requirements

### Requirement: Сборка статики командой источника

Запись `web:` MAY объявлять команду сборки `build`. Сборочное окружение витрины SHALL исполнять её с рабочим каталогом — корнем свежего клона репозитория-источника — передавая каталог вывода аргументом `--out <каталог>`; результат сборки — статика для публикации. Команда SHALL завершаться кодом 0 и оставлять `index.html` в каталоге вывода. Провал команды, превышение таймаута или отсутствие `index.html` SHALL приводить к пропуску записи с предупреждением; сборка витрины MUST NOT падать.

#### Scenario: Успешная сборка

- **WHEN** команда завершилась с кодом 0 и оставила `index.html` в каталоге вывода
- **THEN** статика публикуется в `_site/apps/<slug>/`

#### Scenario: Приоритет результата сборки

- **WHEN** у записи объявлены и `build`, и папка `web/`
- **THEN** публикуется результат сборки, а не содержимое папки `web/`

#### Scenario: Провал команды

- **WHEN** команда завершилась с ненулевым кодом
- **THEN** в логе предупреждение со слагом, страница и карточка пропущены, остальная витрина публикуется; сборка MUST NOT падать

#### Scenario: Результат без index.html

- **WHEN** команда завершилась успешно, но в каталоге вывода нет `index.html`
- **THEN** в логе предупреждение со слагом, страница и карточка пропущены; сборка MUST NOT падать

#### Scenario: Таймаут команды

- **WHEN** команда не завершилась за отведённое время
- **THEN** она прерывается, в логе предупреждение со слагом, страница и карточка пропущены; сборка MUST NOT падать

#### Scenario: Запись без команды сборки

- **WHEN** запись не объявляет `build`
- **THEN** статика берётся из папки `web/` источника, как раньше
