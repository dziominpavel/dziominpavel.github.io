# Design

## Context

- Публикация веб-приложений сегодня: `load_web_registry` (repo/title/description/data) → `collect_web_projects`: `clone_project` (`git clone --depth 1`, таймаут 300 с) → критерий успеха — `web/index.html` → дата карточки (`updated` из файла `data:` либо коммит-дата `web/` через GitHub API, fallback — HEAD клона → дата сборки) → `render_site`: `shutil.copytree(web_dir → _site/apps/<slug>/)`, файл `data:` копируется рядом, URL добавляется в sitemap.
- Иконка карточки — `web/icon.*`, иначе буквенный плейсхолдер. Страница обязана содержать навигацию в каталог; сейчас её даёт сама статика (у Benchmark `web/` рукописная и store-стилизованная).
- Оповещение об обновлении шлёт workflow источника (`notify-store.yml` в Benchmark) через `repository_dispatch`; cron витрины (*/30) — страховка.
- `tests/validate_site.py` применяет store-chrome требования (og/meta/favicon/nav «О проекте» и «Главная», theme.js, `data-theme`, `lang`, charset) к каждому HTML-файлу `_site/` и требует полного покрытия sitemap. Это выполнимо для store-стилизованной статики, но не для произвольного UI приложения.
- Ограничения: бесплатно, без внешних сервисов; Python + pyyaml; деплой GitHub Pages из Actions; версионирование и changelog — по правилам корня.

## Goals / Non-Goals

**Goals:**

- Generic-механизм: запись реестра объявляет команду сборки, витрина исполняет её над свежим клоном и публикует результат — без производных артефактов в git источника.
- Ноль изменений для существующих записей без `build` (instagram-tracker продолжает публиковаться из `web/`).
- Провал сборки не роняет витрину (skip + WARN, как «источник недоступен»).

**Non-Goals:**

- Не менять релизный контракт скачиваемых приложений (store.yaml, version, скриншоты, артефакты).
- Не строить кэш сборок или хранилище артефактов.
- Не менять страницу-каталог и её облик.

## Decisions

**D1. `build:` — строка-команда в записи `web:`.**
Одна запись = одно приложение; команда исполняется в корне свежего клона. Альтернативы: коммит производной статики в источник (отклонено — производные в git, ручное обновление; так живёт текущий Benchmark) и отдельный репозиторий/ветка артефактов (лишняя инфраструктура для бесплатного статического сайта).

**D2. Интерфейс команды: `--out <каталог>`, код 0, `index.html`.**
Витрина создаёт каталог вывода (временно, вне клона) и передаёт его аргументом; cwd — корень клона. Альтернативы: env-переменная (менее явно), фиксированный путь внутри клона (магия). Критерий успеха результата — `index.html`, как у папки `web/`.

**D3. Исполнение и провалы: subprocess без shell, таймаут 300 с, skip + WARN.**
Успех — код 0 и `index.html` в каталоге вывода; иначе WARN со слагом и хвостом вывода команды (последние ~20 строк), запись пропускается, остальная витрина публикуется. Таймаут — как у `clone_project`.

**D4. Дата карточки: `data:` — как было; для `build` без `data:` — дата HEAD клона.**
Контракт даты не расширяем: `updated` из объявленного файла данных остаётся основным (Benchmark его сохраняет; сверка `updated` с коммитом данных работает как раньше). Для build-записей без `data:` коммит-дата `web/` не запрашивается (папки может не быть) — берётся `head_commit_date(project_dir)`; fallback-цепочка (дата сборки + WARN) сохраняется.

**D5. Иконка — из каталога публикуемой статики.**
Поиск `icon.*` ведётся в выбранном источнике (каталог вывода для `build`, `web/` иначе); буквенный плейсхолдер при отсутствии — как раньше. Копирование файла `data:` рядом со страницей сохраняется без изменений контракта.

**D6. `validate_site.py` скоупит store-chrome проверки.**
Полный набор требований (og/meta/favicon/nav «О проекте» и «Главная», theme.js, `data-theme`, `lang`, charset) применяется к страницам самой витрины; для страниц приложений (`_site/apps/**`) — общие проверки: сбалансированность HTML, `lang="ru"`, отсутствие шаблонных остатков. Sitemap обязан покрывать store-страницы и landing-страницы приложений (`/apps/<slug>/`); глубокие подстраницы слепка в sitemap не требуются. Причина: chrome — собственность UI приложения; требовать store-навигацию от полного слепка консоли нельзя (у него своя навигация, плашка «только просмотр» и консольный стиль).

**D7. Окружение сборки.**
В `build.yml` добавляется `pip install pyyaml flask`: Flask нужен команде Benchmark (экспорт поднимает её приложение через test_client). Альтернатива — протокол requirements-файлов источников — избыточна для одной команды; список расширяется по мере появления новых сборок.

**D8. Оповещение — на стороне источника; приём витрины не меняется.**
Пути workflow (`tools/**` у Benchmark) — правка в репозитории-источнике (change `static-mirror-export`); витрина уже принимает `repository_dispatch` и cron-страховку. Спека обновляется дельтой: триггеры — статика, её источник, файл данных.

**D9. Порядок внедрения и пилот.**
Сначала реализуется Benchmark (его change), затем витрина: exec-хук + `build:` у записи `benchmark`, а папка `web/` в Benchmark удаляется после успешной публикации (задача этого change'а). До переключения витрина работает как раньше. Rollback: до удаления `web/` — убрать `build:` (вернётся публикация папки); после — откат коммитов обоих репозиториев.

## Risks / Trade-offs

- [Команда зависает] → таймаут 300 с и прерывание; витрина не падает.
- [Команда требует сеть/зависимости] → раннер имеет сеть, но контракт — автономный статический вывод; зависимости команды фиксируются в D7.
- [Рост времени сборки витрины] → сейчас одна тяжёлая команда; предупреждения порогов печатает экспорт Benchmark; при следующей тяжёлой сборке вернуться к кэшированию (см. Open Questions).
- [Безопасность: команда из реестра исполняется на раннере] → реестр ведёт владелец, чужие репозитории в него не попадают, shell не используется. Риск принят.
- [Регрессия существующей публикации instagram-tracker] → ветка без `build` не меняется; тесты на обратную совместимость обязательны.
- [Ослабление validate_site для страниц приложений] → ослабление ровно до общих проверок (balanced, ru, остатки); store-страницы сохраняют полный набор; тесты валидатора обновляются.

## Migration Plan

1. Benchmark реализует экспорт (change `static-mirror-export`); публикация не меняется.
2. Витрина: exec-хук + `build: python tools/export_web.py` в записи `benchmark`; локальная проверка `python generate.py --out _site` и `python tests/validate_site.py _site`; пуш → деплой.
3. Приёмка страницы `/apps/benchmark/`; после — удаление `web/` в Benchmark (задача этого change'а).
   Rollback: см. D9.

## Open Questions

- Кэширование или инкрементальные сборки при росте числа и тяжести команд — отдельный change по факту.
- Полный протокол зависимостей источников (requirements/uv) — вернуться при появлении второй сборки с нестандартными зависимостями.
