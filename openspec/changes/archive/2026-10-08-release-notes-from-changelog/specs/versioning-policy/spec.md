# Delta: versioning-policy

## ADDED Requirements

### Requirement: Секция changelog начинается с пользовательского саммари
Секция `## [Unreleased]` и свёрнутая из неё версионная секция `## [X.Y.Z]` MUST начинаться с пользовательского саммари: 2–5 строк, описывающих изменения так, как их заметит использующий приложение человек, идущих **выше первой строки** `###`. Категории (`### Добавлено`, `### Исправлено` и аналоги) MUST размещаться ниже саммари и MUST содержать инженерские детали: change-id, состав изменений, результаты тестов, метрики. Один и тот же текст MUST служить и источником заметок GitHub-Release, и историей проекта — отдельное описание релиза писаться MUST NOT.

#### Scenario: Саммари и категории
- **WHEN** в `[Unreleased]` добавляется новая доработка
- **THEN** её короткое описание добавляется в блок выше первой строки `###`, а детали — в соответствующую категорию ниже

#### Scenario: Секция только из категорий
- **WHEN** весь текст секции размещён под строками `###`
- **THEN** это нарушение политики: release-скрипт откажет в подготовке релиза

#### Scenario: Историческая секция без категорий
- **WHEN** версионная секция не содержит ни одной строки `###`
- **THEN** вся её секция считается саммари и может стать телом GitHub-Release без доработки

## MODIFIED Requirements

### Requirement: Changelog обязателен в каждом проекте
Каждый проект владельца MUST содержать файл `CHANGELOG.md` в корне. Changelog MUST вести историю на русском языке и MUST содержать сверху секцию `## [Unreleased]`, а ниже — выпущенные версии в формате `## [X.Y.Z] — дата (УРОВЕНЬ)`. Первичное заполнение MUST покрывать прошлое истории проекта сводной секцией и секциями на существующие теги; сборочные номера, не бывшие релизами, в changelog MUST NOT перечисляться. Под сборочными номерами здесь понимаются номера сборок вида `X.Y.Z.N` и `X.Y.Z.N-g<sha>` — а не версионные секции, сложившиеся до внедрения release-скрипта: такие секции сохраняются как до-релизная история проекта и MUST NOT переписываться, склеиваться или удаляться. Релизные правила действуют с момента появления конвейера.

#### Scenario: Проект без changelog
- **WHEN** у проекта из перечня владельца отсутствует `CHANGELOG.md`
- **THEN** это считается нарушением политики и устраняется при ближайшей покатке

#### Scenario: История без тегов
- **WHEN** у проекта есть коммиты, но теги отсутствуют
- **THEN** прошлое отражается одной сводной секцией, а не попунктной реконструкцией каждой сборки

#### Scenario: Секции до внедрения release-скрипта
- **WHEN** в changelog есть версионные секции, не ставшие git-тегом, потому что конвейер был внедрён позже (например, FogMap 1.0.0–1.5.0)
- **THEN** эти секции остаются в changelog в исходном виде, и их наличие не считается нарушением политики

#### Scenario: Номер сборки в changelog
- **WHEN** в changelog попадает номер сборки вида `1.5.2.39` или `1.5.2.39-g1a2b3c4`, не ставший релизом
- **THEN** это нарушение политики: такой номер MUST быть убран из changelog
