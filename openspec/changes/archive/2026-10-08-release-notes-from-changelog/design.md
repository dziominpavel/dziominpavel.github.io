# Design: release-notes-from-changelog

## Context

Эталон `scripts/release.ps1` (корень, `$SCRIPT_VERSION = "1.2.0")` раздаётся копиям в 7 репозиториев через `scripts/sync-release.ps1`. Публикация выполняется одной строкой `gh release create $Tag @Staged --title $Tag --verify-tag` — без `--notes*`, поэтому тело релиза пустое у всех 11 опубликованных релизов.

Changelog при этом читается скриптом дважды и по-разному: `Read-Changelog` (шаг подготовки) использует `[System.IO.File]::ReadAllText` (UTF-8), а проверка наличия секции на публикации — `git show HEAD:CHANGELOG.md`, вывод идёт через консоль PowerShell. Для содержимого второго способа это безопасно только потому, что результат используется лишь для поиска регулярки `^## \[X.Y.Z\]`; в буфер заметок так писать нельзя.

Фикстуры `tests/test_release_phases.py` строят фейковый `gh` (`.cmd`/shell-шлём), который возвращает код выхода, но **не фиксирует аргументы**. Настоящий `notes.txt` в фикстурах — это «грязный файл» для проверки отказа публикации, к заметкам релиза он отношения не имеет.

Конфликт со спекой «Changelog обязателен в каждом проекте» (`versioning-policy`) решён в пользу узкого прочтения: правится дельтой, история FogMap 1.0.0–1.5.0 не переписывается. Подробнее — в proposal.md.

## Goals / Non-Goals

**Goals:**

- Тело каждого нового GitHub-Release = текст из `CHANGELOG.md`, без второго источника описания.
- Лаконичность тела обеспечивается структурой секции (саммари до `###`), а не отдельным текстом.
- Пустое тело физически невозможно выпустить: отказ происходит на подготовке, до сборки `dist/`.
- Кириллица и типографика доходят до GitHub без искажений.
- Все 7 копий скрипта ведут себя одинаково.

**Non-Goals:**

- Показ «что нового» на странице приложения витрины (`generate.py`, `releases/latest`) — отдельный change.
- Восстановление тегов и релизов за версии 1.0.0–1.5.0 FogMap.
- Автоматическое сжатие/саммаризация секций (LLM, правила) — саммари пишет автор.
- Изменение формата ассетов, имён тегов, порядка фаз и порядка `Prepare` → сборка → публикация.

## Decisions

**1. Срез = блок до первой `###`; пустой блок → отказ, а не фолбэк.**
Альтернатива «если до `###` пусто — брать всю секцию» отвергнута: она допускает тело в 8–10 КБ (как секция 1.6.0) и оставляет норму саммари пожеланием. Отказ в `-Prepare` даёт раннюю и однозначную обратную связь. Обратная сторона правила — исторические секции без `###` автоматически становятся телом целиком, поэтому бэкфилл и новые релизы используют одно правило чтения.

**2. Источник — локальный `CHANGELOG.md` через `Read-Changelog`.**
Альтернатива `git show HEAD:CHANGELOG.md` отвергнута: декодирование конвольного вывода PowerShell на кириллице даёт мусор. Дерево на момент публикации гарантированно чистое (шаг публикации допускает грязь только в `version`/`CHANGELOG.md` и коммитит их раньше), поэтому локальный файл и есть `HEAD:CHANGELOG.md`. Запасной вариант, если чистота перестанет гарантироваться — `git show ... --output=<file>` (сырые байты), но он не нужен при текущем порядке фаз.

**3. Транспорт — временный файл + `--notes-file`, UTF-8 без BOM.**
Альтернатива `--notes "..."` отвергнута: переносы строк и кавычки в PowerShell ломают аргумент, а тело до нескольких килобайт неудобно передавать как строку. Файл создаётся через `[System.IO.Path]::GetTempFileName()`, пишется `UTF8Encoding($false)` (BOM — ошибка разбора JSON на стороне GitHub API, тот же приём уже применён для `repository_dispatch`), удаляется в `finally`.

**4. Тело тега = тело релиза; заголовок релиза не меняется.**
`-m` сейчас всегда `"Release $Tag"` — тег является второй точкой входа в историю и логично наполняется тем же текстом. `--title $Tag` остаётся: единообразие ссылок и поиска важнее, чем дата в заголовке.

**5. Гейт живёт в `-Prepare`, а не на публикации.**
Причина: отказ до сборки экономит время и соответствует существующему разделению (подготовка = до `dist/`, публикация = проверки непосредственно перед тегом). Дополнительная проверка непустоты заметок на публикации не дублируется — публикация и так требует пройденной подготовки и чистого дерева.

**6. Бэкфилл — `gh release edit --notes-file`, текст секции целиком, все 11 релизов.**
`edit` не меняет метку `latest`, поэтому витрина (`generate.py` → `releases/latest`) продолжит отдавать актуальную версию. Бэкфилл тегов за 1.0.0–1.5.0 отвергнут: свежесозданный релиз стал бы `latest` (дата публикации свежее), а артефактов APK за те версии не сохранилось — получились бы релизы без файлов. Бэкфилл разовый, одной командой на репозиторий, с проверкой результата `gh release view`.

**7. Рассылка — бамп эталона и `sync-release.ps1`.**
`$SCRIPT_VERSION` 1.2.0 → 1.3.0 (спека требует печатать версию для контроля расхождения копий), затем штатная рассылка корневым скриптом. Ручные правки копий в дочерних репозиториях запрещены — там должна появиться ровно та же версия эталона.

**8. Тесты: шлём `gh` дописывает аргументы в лог.**
Чтобы проверить не только код выхода, но и содержимое заметок, фейковый `gh` в фикстурах дописывает свои аргументы (включая содержимое файла из `--notes-file`) в постоянный лог в рабочей директории фикстуры — на момент вызова шлёма временный файл ещё существует. Альтернатива «не удалять notes-файл» отвергнута: оставляет мусор в реальной работе ради теста.

**9. Правится только требование «Changelog обязателен в каждом проекте».**
Требование «Бамп версии только на релизе» не трогается: его норма адресована текущему процессу, а её артефактов в прошлом не осталось — файл `version` сейчас равен реально выпущенной `1.6.0`. Менять требование ради гипотетической придирки — расширение объёма без выигрыша.

## Risks / Trade-offs

- **Мусор в заметках из-за кодировки** (кириллица, `—`, `≥`) → чтение через `Read-Changelog`, запись UTF-8 без BOM, отдельный тест с кириллической секцией и сверкой тела.
- **Копии разъезжаются, если рассылка не выполнена** → `$SCRIPT_VERSION` печатается при каждом запуске, `sync-release.ps1` сверяет эталон с копиями; версия скрипта бампается в том же коммите, что и его код.
- **Ломаются существующие фикстуры** (`###` — первая строка Unreleased) → все фикстуры, участвующие в подготовке/публикации, получают строку саммари; это ожидаемая правка, а не обход проверки.
- **Бэкфилл упадёт на середине списка** → операция идемпотентна (`edit` заменяет тело), повтор безопасен; порядок — от последнего релиза к первому, чтобы при обрыве больше всего выиграли свежие.
- **Секция окажется больше лимита GitHub** (~125k символов) → текущие секции ≤ 10 КБ, запас двукратный; отдельная проверка не вводится как избыточная.
- **Норма саммари ужесточает подготовку** → ошибка формулируется с подсказкой (что добавить и куда), а не общим «ошибка формата».

## Migration Plan

1. Спеки (дельты этого change) и документация: `docs/versioning.md`, `docs/agents-versioning-block.md`, пункт в `## [Unreleased]` changelog корня.
2. Эталон `scripts/release.ps1` (заметки, гейт, бамп 1.3.0) и `tests/test_release_phases.py`.
3. Прогон тестов корня.
4. Рассылка `sync-release.ps1` в 7 репозиториев, проверка печатаемой версии скрипта в каждой копии.
5. Одноразово: удаление второго `## [Unreleased]` в `CHANGELOG.md` FogMap.
6. Одноразово: бэкфилл 11 релизов телами секций, сверка `gh release view` по каждому.

Откат: revert коммита + повторная рассылка (скрипт вернётся к 1.2.0 и к пустым телам у новых релизов). Опубликованные теги и релизы не перезаписываются; тела бэкфилла откатываются `gh release edit <tag> --notes ""`, если понадобится.

## Open Questions

- Показывать ли блок «что нового» на странице приложения витрины — влияет на `generate.py` и контракт стора, решается отдельным change.
- Нужен ли жёсткий лимит длины саммари (например, 5 буллетов формально) — сейчас это норма в документации, не проверка; можно ужесточить позже без изменения спек.
