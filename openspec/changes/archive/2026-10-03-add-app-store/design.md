## Context

Motivation и состав — см. proposal.md. Ключевые факты текущего состояния: 7 публичных репозиториев приложений под owner `dziominpavel` (5 Android/Gradle, 1 Go→zip, 1 Python→PyInstaller exe); `gh` не установлен; Python 3.14 установлен; `store.yaml`/файлы `version` (кроме FogMap) отсутствуют; у FogMap есть `build-apk.bat` (сборка в `dist/`, без git/release) и `dist/archive` с историческими APK. Основные решения уже приняты владельцем при grilled-interview (см. proposal), здесь — техническая архитектура их исполнения.

## Goals / Non-Goals

**Goals:**
- нулевая ручная работа при релизе: владелец собирает → запускает release-скрипт → всё остальное происходит само;
- «приложения не знают о сторе» — контракт только на данных (файлы), ни одного упоминания стора в коде/скриптах приложений, кроме самой публикации релиза (общая практика GitHub);
- один источник правды на версию (файл `version` → tag → release) и на описание (`store.yaml`);
- отказоустойчивость: битый проект не валит витрину.

**Non-Goals:**
- Google Play / F-Droid / подпись сертификатом (деньги — вне скоупа);
- платёжная система, аккаунты, корзина, рейтинги, комментарии;
- changelog/история версий (поле `history` резервируется, не реализуется);
- англоязычная версия, кастомный домен;
- автоматическая автосъёмка скриншотов (adb-опция отложена).

## Decisions

**D1. Стор — отдельный репозиторий `dziominpavel.github.io`, сайт по корневому домену.**
Альтернатива: репо с путём `/<name>` — путь в URL, менее презентабельно. Корневой репо с именем владельца — стандартный приём GitHub Pages, бесплатно, без настроек.

**D2. Контракт на данных, не на поведении (data contract, читатель-паттерн).**
Стор — независимый сканер `registry.yaml`; приложения только кладут `store.yaml`/`screenshots/`/`version`. Альтернативы отклонены: repository_dispatch (приложение «знает» о сторе — нарушает принцип), локальный скрипт-обходчик (живёт на одной машине, забыл — стор отстал). Стор-CI читает всё сам.

**D3. Хранение бинарей — GitHub Releases, не git/LFS/`dist/` в истории.**
git не хранит бинари нормативно (жёсткий лимит 100МБ/файл, разрастание истории), LFS бесплатен лишь на 1ГБ/1ГБ-мес. Releases: файлы вне истории, 2ГБ/файл, практически безлимитный трафик, вечные URL, обычная open-source-практика. `dist/` остаётся локальным staging'ом (gitignored — уже так).

**D4. Единый release-скрипт: копия в каждом репо + версия скрипта в выводе.**
Рассмотрены: self-update из репо стора (сеть как предусловие запуска, точка отказа), git submodule (болезнь обновлений). Копии самодостаточны и работают офлайн; риск рассинхрона снимается печатью версии скрипта и командой разноса копий (скрипт-обновитель в tasks). Поведение: читает `version` → проверяет иконку и `dist/` → `git tag vX.Y.Z` → `gh release create` c ассетами. Применяется к проектам как «билд положил в dist/ → release-скрипт опубликовал».

**D5. Платформы — авто-детект по маскам ассетов (`*.apk`, `*-win*.zip`, `*.exe`), поле `platforms` запрещено валидацией.**
Альтернатива (ручное поле) отклонена как источник рассинхрона («забыл дописать — кнопки нет»). Несколько ассетов одной платформы → показ всех как вариантов. Неизвестные ассеты игнорируются, не ломая сборку.

**D6. Генератор — Python (stdlib + PyYAML), шаблоны — обычный HTML/CSS + крошечный JS.**
Альтернативы: Node (новая экосистема ради 11 страниц), PowerShell/bash (хрупко на YAML/шаблонах). Python уже есть в инфраструктуре владельца (`check-version.py`, Actions). Фреймворки отклонены: статика из данных не оправдывает тяжесть; современный вид — CSS-переменные, сетки, transitions, system font stack.

**D7. Синхронизация — cron GitHub Actions (каждые 30 мин) + триггер по push `registry.yaml`; генерация статики в CI, коммит готовой статики в ветку деплоя.**
Деплой Pages — из CI репо стора (Actions бесплатны для публичных). Ручная локальная сборка — только для превью при разработке шаблонов. Задержка до 30 мин приемлема: кнопка «Скачать» ведёт на свежий релиз всегда (URL ассета не зависит от витрины), отстаёт только метаданные карточки.

**D8. Источники данных карточки:** версия/размер/дата/ссылки/`download_count` — GitHub API (`releases/latest`); тексты/иконки/скриншоты/requirements — `store.yaml` и файлы проекта. Разделение зон владения исключает конфликт записей (CI не трогает описание, владелец не вводит версию).

**D9. Иконка обязательна, enforcement — в release-скрипте (fail-fast), плюс мягкий skip в генераторе.**
Скрипт не даёт опубликовать релиз без иконки (новый проект физически не может попасть на витрину битым), а генератор при этом всё равно skip'ит с варнингом, а не падает — двойная страховка без нарушения инварианта «битый проект ≠ падение витрины».

**D10. Rollout — пилот на FogMap, затем скрипт-волна на остальные 6.**
Ошибки контракта (формат ассета, slug, иконки) всплывают на одном проекте. Для instagram-tracker добавляется шаг сборки PyInstaller-exe (один файл, `--onefile`); для YandexMusicDownloader — упаковка `app.exe`+`ffmpeg.exe` в `Compress-Archive`-zip. Для проектов без `version` — заводятся файлы `version` (текущие версии фиксируются при внедрении).

## Risks / Trade-offs

- [Скрипты-копии разъедутся по версиям] → скрипт печатает свою версию; задача — скрипт-обновитель, разносящий эталон по репо; на старте разнос ручной (7 копий).
- [PyInstaller-exe триггерит SmartScreen/антивирусы] → честная подсказка на странице приложения (spec store-catalog); сертификат — вне скоупа (платный).
- [Нестандартный ассет не опознан авто-детектом] → маски в одном месте (генератор); дефолтное поведение — игнор с логом, витрина не падает; известные форматы покрывают все 7 проектов.
- [Rate limit GitHub API в cron] → в Actions использовать `GITHUB_TOKEN` (5000/час хватает с запасом: ≤7 запросов на сборку).
- [Отсрочка метаданных до 30 мин] → осознанный trade-off (D7); снимается опциональным `workflow_dispatch`/repository_dispatch позже, без изменения specs (поведение «в течение одного цикла» уже заложено).
- [Приватность: всё публично] → владелец подтвердил публичность репозиториев и описаний; контакты — только GitHub-профиль, личных данных на витрине нет.
- [GoatCounter — внешний сервис] → безcookie и бесплатен; при отказе — одна строка удаляется из шаблона, витрина работает.
- [Привязка к репо потребителя] → change живёт в репо стора; пилотные работы в FogMap (store.yaml, release-скрипт) выполняются в его собственном change/задачах FogMap, дельта-спеки стора capability FogMap не модифицируют, конфликтов требований нет.

## Migration Plan

1. Установка `gh` + авторизация; локальный репозиторий `dziominpavel.github.io` уже создан и инициализирован (git + OpenSpec) — осталось создать публичный remote на GitHub и выполнить первый push (по команде владельца).
2. Пилот FogMap: контракт (icon/version/screenshots/store.yaml) → release-скрипт → первый релиз → генератор + шаблоны → cron → Pages. Точка невозврата отсутствует: до пуша витрина не видна.
3. Волна: скрипт-обновитель разносит release-скрипт и заготовки `store.yaml` на 6 проектов; владелец заполняет описания (черновики готовит ассистент) и иконки для YMD/instagram.
4. Первые релизы остальных 6 → cron сам подхватывает.
Rollback: удалить/приватизировать репо стора — витрина исчезает, релизы приложений и их репозитории не затронуты; release-скрипт откатывается удалением копии.
