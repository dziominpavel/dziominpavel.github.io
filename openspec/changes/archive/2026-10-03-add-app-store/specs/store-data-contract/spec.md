## Purpose

Единый контракт данных между репозиториями приложений и статическим стором: какие файлы и поля обязан содержать каждый проект, как стор их читает и что происходит при нарушении контракта.

## ADDED Requirements

### Requirement: Обязательные файлы контракта в репозитории приложения
Каждый репозиторий приложения, входящий в реестр стора, MUST содержать: файл `store.yaml` в корне, папку `screenshots/` (3–5 изображений единого формата), файл иконки png (512×512, путь указан в `store.yaml`), файл `version` (формат `MAJOR.MINOR.PATCH`). Файл `store.yaml` MUST содержать поля: `name`, `description`, `icon`. Поле `requirements` (системные требования, одна строка) является опциональным. Поле `history` зарезервировано под changelog и в первой версии MUST оставаться пустым или отсутствовать.

#### Scenario: Валидный проект
- **WHEN** репозиторий из реестра содержит все обязательные файлы и поля
- **THEN** стор включает его данные в сборку витрины без предупреждений

#### Scenario: Отсутствует обязательное поле
- **WHEN** в `store.yaml` отсутствует поле `name`, `description` или `icon`
- **THEN** проект пропускается при сборке витрины с предупреждением в логе CI; сборка витрины MUST NOT падать

### Requirement: Реестр проектов в репозитории стора
Репозиторий стора MUST содержать файл `registry.yaml` со списком репозиториев приложений. Ключ записи MUST соответствовать паттерну `[a-z0-9-]` и служить слагом страницы приложения (`/<key>/`). Добавление нового приложения в стор MUST требовать только добавления одной записи в `registry.yaml` (при условии выполнения контракта в самом репозитории).

#### Scenario: Добавление восьмого проекта
- **WHEN** владелец добавляет запись в `registry.yaml`, а в репозитории проекта выполнен контракт
- **THEN** после ближайшей синхронизации проект появляется на витрине без правок кода стора

#### Scenario: Некорректный ключ реестра
- **WHEN** ключ записи в `registry.yaml` не соответствует `[a-z0-9-]`
- **THEN** запись отклоняется валидацией с предупреждением; остальные записи обрабатываются

### Requirement: Разделение зон владения данными
Секция данных описания (`name`, `description`, `icon`, `requirements`, `screenshots/`) MUST редактироваться только владельцем вручную и MUST NOT изменяться автоматической синхронизацией. Данные о релизе (версия, ссылка на ассет, размер, дата, счётчик скачиваний) MUST получаться стором из GitHub Releases и MUST NOT дублироваться в `store.yaml`.

#### Scenario: Синхронизация не затирает описание
- **WHEN** CI стора выполняет плановую синхронизацию
- **THEN** поля `name`, `description`, `icon`, `requirements` в репозиториях приложений остаются без изменений; обновляются только производные данные релиза

#### Scenario: Рассинхрон версии невозможен
- **WHEN** в `store.yaml` присутствует поле с версией
- **THEN** валидация помечает его как лишнее (версия берётся исключительно из GitHub Release)

### Requirement: Проект без релиза скрыт
Приложение из реестра, у которого нет ни одного GitHub-Release или у последнего релиза отсутствуют ассеты, MUST быть полностью скрыто на витрине (ни карточки, ни страницы).

#### Scenario: Проект в разработке
- **WHEN** репозиторий в реестре содержит контракт, но не имеет релизов
- **THEN** на витрине нет ни карточки, ни страницы, ни упоминания этого приложения

#### Scenario: Первый релиз опубликован
- **WHEN** у ранее скрытого приложения появляется первый GitHub-Release с ассетами
- **THEN** после ближайшей синхронизации приложение появляется на витрине
