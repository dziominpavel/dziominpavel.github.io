# Design

## Context

См. `proposal.md` — Why. Текущее состояние:

- `versioning.yaml` описывает `storefront` как `track: static`, `version_file: null`, `release: false`.
- Файла `version` в корне нет; `scripts/check-version.py` в самопроверке определяет трек по наличию `version`/`VERSION`/`pyproject.toml`.
- Страница «О проекте» собирается из `ABOUT_TEMPLATE` в `generate.py`; общий футер задан в `BASE_TEMPLATE` и одинаков для всех страниц.
- У витрины нет `release.ps1`; деплой статики идёт через GitHub Actions по пушу в `main`.
- У остальных приложений версия хранится в `version`, тег — `vX.Y.Z`, заметки релиза берутся из пользовательского блока changelog.

## Goals / Non-Goals

**Goals:**

- Дать витрине собственную версию и первый тег/Release, не заводя отдельный release-конвейер.
- Показать версию внизу страницы «О проекте» и дать ссылку на историю версий.
- Сохранить работоспособность сборки при отсутствии/порче файла `version`.

**Non-Goals:**

- Автоматизация релиза витрины: release-скрипт, артефакты в `dist/`, автосоздание тега из CI.
- Показ версии витрины в общем футере или на других страницах.
- Версионирование веб-приложений и изменение контракта приложений.
- Переписывание истории changelog: накопленный `[Unreleased]` становится первой версией.

## Decisions

### D1. Релизный трек без release-скрипта

`storefront` переводится в `track: release`, `version_file: version`, `release: false`. Версия хранится в новом файле `version` (`1.0.0`). Тег `v1.0.0` и GitHub Release создаются вручную после пуша: у витрины нет артефактов, а деплой уже выполняет GitHub Actions. Это тот же режим, что у Benchmark (`release: false`, ручные теги и Release).

Альтернативы: оставить статический трек и показывать «версию» из коммита (не соответствует запросу и не даёт тегов); завести `release.ps1` с `dist/` (лишняя сущность для статики, дублирует деплой).

### D2. Версия только внизу «О проекте»

Строка добавляется в конец `ABOUT_TEMPLATE`, после кнопки «Смотреть приложения»: `Версия витрины: 1.0.0 · История версий`. Ссылка ведёт на `https://github.com/dziominpavel/dziominpavel.github.io/releases`. Общий футер не трогаем: версия не дублируется на главной и страницах приложений, как и выбрано.

Альтернативы: общий футер (версия на каждой странице, больше шума); отдельная страница истории версий (лишняя сущность, GitHub Releases уже даёт историю).

### D3. Чтение версии с мягким отказом

Генератор читает `version` в момент рендера. Значение проверяется регулярным выражением `MAJOR.MINOR.PATCH`; при отсутствии файла, ошибке чтения или невалидном значении строка не выводится и в stderr идёт `[WARN]`, сборка продолжается. Функция чтения принимает путь, чтобы тесты не зависели от рабочего каталога.

Альтернативы: жёстко падать без `version` (статический сайт не должен ломаться из-за одного файла); хардкодить версию в шаблоне (рассинхрон с тегом).

### D4. Заметки первого релиза — из changelog

Пользовательский блок `CHANGELOG.md` (строки выше первого `###`) становится заметками GitHub Release `v1.0.0`; инженерные детали под `###` в заметки не попадают. Это повторяет правило остальных проектов и не требует отдельного описания релиза.

### D5. Тесты

- `read_storefront_version`: валидный `1.0.0`, отсутствующий файл, мусорное значение.
- Рендер «О проекте»: строка с версией и ссылкой стоит после CTA; при отсутствии версии строки нет, страница собирается.
- Главная и страница приложения не содержат строку версии витрины.
- `scripts/check-version.py` проходит в режиме самопроверки после появления `version` и версионной секции.

## Risks / Trade-offs

- **Забудут поднять версию при следующем релизе** → `check-version.py` сверяет `version` с верхней версионной секцией; рассинхрон ловится до тега.
- **Первый Release будет большим: в него войдёт весь накопленный `[Unreleased]`** → это ожидаемая история первого релиза; блок уже соответствует формат-контракту.
- **Ссылка на Releases окажется пустой до создания релиза** → тег и Release создаются тем же изменением до проверки живой страницы.
- **Файл `version` потеряется при локальной сборке** → версия не отображается, но сайт собирается; WARN в логе.
- **Версия на «О проекте» устареет между релизами** → так и задумано: между релизами номер заморожен, меняется только на релизе.

## Migration Plan

1. Добавить `version` (1.0.0), перевести `storefront` на релизный трек, реализовать вывод и тесты.
2. Закоммитить, запушить `main`; дождаться деплоя GitHub Pages.
3. Свернуть `[Unreleased]` в `## [1.0.0] — 2026-10-24 (MINOR)`, обновить `version` и changelog, повторно проверить `check-version.py`.
4. Поставить тег `v1.0.0`, запушить его, создать GitHub Release с пользовательским блоком.
5. Проверить живую страницу `/about/`: версия и ссылка на месте.
6. Откат: убрать строку версии из шаблона и вернуть `storefront` в `track: static`; тег и Release удалить вручную, если релиз отменяется.
