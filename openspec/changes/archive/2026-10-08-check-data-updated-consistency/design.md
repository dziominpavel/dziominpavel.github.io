# Design: check-data-updated-consistency

## Context

Мотивация и объём — в `proposal.md`. Здесь — только то, что определяет подход.

Факты, влияющие на решения:

- Ветка даты живёт в `collect_web_projects` (`generate.py:364-394`): при объявленном `data:` дата карточки читается из поля `updated` файла данных, иначе — из коммита `web/`.
- Клон источника — **shallow**: `git clone --depth 1` (`generate.py:246`). В нём ровно один коммит, поэтому `git log -- data/index.json` вернёт результат, только если этот единственный коммит и трогал файл данных, — то есть в интересующем нас сценарии (данные менялись раньше) локальный гит молча даст пусто.
- Уже есть хелпер получения коммит-даты через GitHub API — `fetch_web_commit_date(repo, token)` → `commits?path=web&per_page=1` (`generate.py:295`); он возвращает ISO-дату или `None` и пишет WARN при сбое.
- Существующие тесты импортируют `fetch_web_commit_date` и подменяют его как штук (`tests/test_generate.py:24,296,432`), а фикстура уже умеет строить `data/index.json` с полем `updated` (`tests/test_generate.py:203,224`).
- Фактическое значение `updated` в Benchmark — date-only (`2026-10-06`), тестовый фикстур — полный ISO (`2026-01-15T00:00:00Z`).
- Сейчас у `data:` ровно один потребитель (Benchmark), то есть на билд добавляется единичный запрос к API.

## Goals / Non-Goals

**Goals:**

- Рассинхрон `updated` и последнего коммита файла данных становится видимым в логе сборки автоматически, без ручного сравнения дат.
- Стоимость проверки — не более одного запроса к GitHub API на web-запись с `data:`.
- Поведение витрины (дата карточки, статика, код возврата) не меняется ни в одном из исходов.

**Non-Goals:**

- Исправлять источник или как-то форсировать бамп `updated` в репозиториях-источниках — витрина о пайплайнах приложений ничего не знает и знать не обязана.
- Менять правило выбора даты web-карточки (`store-web-apps`, requirement про дату) — оно остаётся `updated` → иначе это был бы другой change.
- Проверять `updated` у скачиваемых приложений — у них дата берётся из `releases/latest`, файла данных нет.
- Вводить в контракт новых полей (`registry.yaml`, `data:`, формат `updated` не меняются).

## Decisions

**D1. Источник даты коммита — GitHub API, а не локальный гит.**
Shallow-клон (`--depth 1`) делает локальный `git log -- <path>` непригодным: ответ зависит от того, трогал ли единственный коммит этот файл. Расширять клон ради проверки — плохой обмен: растёт время каждой сборки ради одного сравнения. Поэтому переиспользуем механизм `fetch_web_commit_date`, вынося путь в параметр: `fetch_path_commit_date(repo, path, token=None)`, а `fetch_web_commit_date` остаётся обёрткой над ним с путём `web`.
*Альтернатива:* `git fetch --deepen` / отказ от `--depth 1` — отклонено: замедляет все сборки и усложняет клонирование ради одного чтения.

**D2. Сравнение — по календарной дате UTC.**
`updated` встречается и в date-only, и в полном ISO-виде, API возвращает ISO. С обеих сторон берётся календарная дата UTC, затем обычное равенство. Совпадение — норма, любое неравенство — WARN: это ловит оба направления ошибки (забыли обновить `updated`, либо обновили `updated`, не меняя данных).
*Альтернатива:* сравнение меток времени напрямую — отклонено: коммит в тот же день давал бы ложное срабатывание.

**D3. Только наблюдательность: WARN без изменения поведения.**
Датой карточки остаётся `updated`, статика и код возврата не меняются. Витрина слабо связана с источниками (приложения о сторе не знают; стор не должен знать устройство их пайплайнов), а WARN в логе `build-site` владелец видит ровно тогда, когда открывает запуск по подозрительной дате.
*Альтернатива A:* брать `max(updated, коммит)` — отклонено: меняет observable-поведение и требует правки существующего requirement даты, то есть раздувает change.
*Альтернатива B:* валить сборку — отклонено: сломанный источник не должен оставлять витрину без обновления (тот же принцип best-effort, что у оповещений из change `add-event-driven-store-sync`).

**D4. Недоступная коммит-дата — сверка пропускается молча.**
У `fetch_web_commit_date` сбой печатает WARN осмысленно: там дата уходит в fallback и это меняет вывод. В сверке же неспособность получить дату — не свидетельство рассинхрона. WARN на каждом билде при rate-limit превратился бы в шум, который перестают читать.
*Альтернатива:* печатать WARN о недоступности сверки — отклонено по той же причине; риск (реальный рассинхрон скрывается за периодом недоступного API) принят: сверка идёт на каждой сборке, их десятки в сутки между cron и событийными триггерами.

## Risks / Trade-offs

- [Ложное срабатывание: переписанная история или сдвиг даты коммита] → сравнение по дате UTC, а не по SHA/времени; стоимость ложного срабатывания — одна строка в логе, не поведение витрины.
- [Дополнительный запрос к API на каждый билд] → `per_page=1`, один потребитель `data:` сейчас; при исчерпании лимита сверка молча пропускается (D4), сборка не страдает.
- [Владелец не заметит WARN] → предупреждение не чинит источник: без внимания дата карточки останется прежней ровно до тех пор, пока пайплайн источника не начнёт бампить `updated` правильно.
- [Дублирование кода получения дат] → один хелпер с параметром пути; имя `fetch_web_commit_date` и его контракт (ISO или `None`) сохраняются, существующие тесты не переписываются.

## Migration Plan

1. Изменение в `generate.py` + тесты → пуш в `main` → штатный запуск `build-site` собирает и деплоит витрину (поведение статики не меняется, меняется только лог).
2. Откат — revert одного коммита генератора: дата карточки нигде не менялась, поэтому миграционных действий и разбора последствий нет.
