# Design: fix-release-notes-audience

## Context

Механика уже есть и не меняется: `Get-ReleaseNotes` (`scripts/release.ps1:151`)
вырезает из секции блок до первой строки `###`, `-Prepare` на `:217` проверяет
только непустоту этого блока, `Resolve-ReleaseLevel` (`:170`) определяет уровень
только по строкам `###`-категорий. Правило «дерево чистое» (`:228`) и записи
файлов идут после гейта — контентный отказ случается раньше, чем что-то
записано. `$SCRIPT_VERSION = "1.3.0"`, все 7 дочерних копий идентичны эталону.

Доставка равномерности — `sync-release.ps1`: локальный канал
(docs/versioning.md, scripts/check-version.py, скелет changelog, AGENTS-блок
по маркерам, release.ps1/bat) и удалённый канал (release.ps1/bat через GitHub
API) на все 12 проектов `versioning.yaml`; в конце скрипт сверяет копии
с эталоном и даёт exit 1 при расхождении. Ручные правки копий запрещены.

Фактическое состояние (проверено через `gh api`): все 11 опубликованных тел
непустые; нечитаемы только три тела FogMap (`v1.6.0` — механика бампа,
`v1.5.2`/`v1.5.1` — дампы секций без `###`); `instagram-tracker` в
`[Unreleased]` начинается сразу с `###`, его следующий `-Prepare` упадёт уже
на сегодняшнем гейте; удаление дубль-секции `## [Unreleased]` в FogMap уже
сделано в рабочем дереве и не закоммичено. `gh` установлен и авторизован.

Мотивация — в proposal.md; поведенческий контракт — в дельтах
`specs/app-release-pipeline/spec.md` и `specs/versioning-policy/spec.md`.

## Goals / Non-Goals

**Goals:**

- Гейт видит ровно тот текст, который увидит пользователь, и отказывает до
  любых записей.
- Один формат-контракт: три эталона в корне (контракт-док, AGENTS-блок,
  release.ps1) + одна команда sync на 12 проектов.
- Корректный уровень релиза при любом валидном блоке, включая секцию только
  с `**Исправлено**` и без `###`-секций.
- Ремонт FogMap и instagram-tracker — контентом, без изменения механики.

**Non-Goals:**

- Рендерер витрины «список версий + изменения» — отдельный change в этом репо.
- Проверка саммари в `check-version.py` (см. Open Questions).
- Тела остальных 8 релизов, секции FogMap `1.5.0` и ниже, переписывание
  сообщений уже созданных git-тегов.
- Отдельное релиз-описание параллельно с changelog.

## Decisions

**1. Валидируем извлечённый блок, а не сырую секцию.**
Гейт работает по результату `Get-ReleaseNotes` — того же вызова, который
пакует `--notes-file`. Это гарантирует: «проверено» = «опубликовано», и логика
вырезания не дублируется. Запрет `###` внутри блока обеспечен конструкцией
(извлечение останавливается на первой `###`); правило «метка — жирная, не
`###`» живёт в доках, потому что `###`-метка в начале блока просто обрежет
его до нуля. Альтернатива (валидировать строки секции выше `###` вручную)
отклонена: два источника правды расходятся.

**2. Метка = строка, целиком являющаяся жирным текстом `**...**`; белого
списка названий нет.**
`^\*\*[^*]+\*\*$` на непустую строку. Словарь категорий — зона
`docs/versioning.md`, не гейта. Причина: документированный маркер
`**BREAKING:**` — самое «пользовательское», что бывает, он MUST проходить
гейт в блоке, а строгий список `Добавлено/Исправлено/Изменено` его завернёт.
Опасный случай (жирная строка с кодом вместо метки) смягчён запретом `` ` ``
и лимитом 140. Альтернатива (белый список из трёх категорий) отклонена
из-за BREAKING.

**3. Классификатор уровня опознаёт и жирные метки.**
`Resolve-ReleaseLevel` дополнительно матчит `^\s*\*\*(Добавлено|Изменено)...`
по тем же корням, что и `###`-строки, сохраняя текущие правила
(BREAKING → MAJOR, наивысший уровень выигрывает). Это не optional:
`versioning-policy` требует «только исправления → PATCH», а секция
только с `**Исправлено**` без `###` сейчас уходит в MINOR-фолбэк
(`:178`). Альтернативы отклонены: требовать `###`-секции гейтом — вторая
точка отказа; принять MINOR-фолбэк — нарушение спеки.

**4. Порядок фаз `-Prepare` сохраняется: контентный гейт → чистое дерево →
классификация → записи.**
Контентный отказ остаётся первым (быстрая обратная связь, ничего не
записано); замена строго на месте `:217`. Сообщение отказа печатает проблемный
блок (или строку) + краткую форму контракта и пометку «это увидят
пользователи» — это видимое поведение, зафиксированное в сценариях дельты.

**5. Правка эталонов в корне, доставка — только sync-ом, версия скрипта 1.4.0.**
Последовательность: доки → скрипт + тесты → `sync-release.ps1 -LocalOnly -Apply`
(локально всем 12) → `sync-release.ps1 -Apply` (release.ps1/bat в 7 релизных) →
коммиты `chore(release): sync release script vN` по команде владельца.
Смена `$SCRIPT_VERSION` обязательна: без неё сверка копий в sync-е
не увидит расхождение.

**6. Ремонт FogMap — блоки, а не переписывание секций.**
`1.6.0`: прозаический верх заменяется блоком «`**Добавлено**` (4 буллета) +
`**Исправлено**` (5 буллетов)», текст буллетов — из существующих
инженерных пунктов, сжатый до «одна строка = одно изменение». `1.5.2`/`1.5.1`:
добавляется блок и вводятся `###`-категории, разбивающие уже существующие
списки (иначе фолбэк «вся секция = заметки» остаётся). Тела выставляются
`gh release edit <tag> --notes-file` из блока закоммиченного changelog —
текст GitHub == текст секции. Удалённый дубль секции коммитится отдельно
до релиза (иначе гейт чистого дерева его заблокирует). Секции `1.5.0` и ниже
не трогаются — их кормит сценарий «Историческая секция без категорий».

**7. instagram-tracker — контентная правка, а не ожидание отказа.**
Верхний блок появляется в `[Unreleased]` сейчас, в рамках этой задачи: ждать
отказа на чужом релизе — значит получать его в случайный момент. Остальные
6 релизных проектов контентно чинить не нужно (их секции/тела проходят
контракт или заморожены как история).

## Risks / Trade-offs

- **Строгий гейт завернёт добротную прозу** → смягчение: печать текста
  с пометкой об адресате, формат-контракт в `docs/versioning.md` и
  AGENTS-блоке (подсказка видна в момент работы), первый отказ — на машине
  владельца до записей.
- **Жирная метка вне словаря категорий** → классификатор вернёт MINOR
  (фолбэк `:178`); BREAKING ловится отдельным regex независимо. Словарь
  зафиксирован в docs — считаем приемлемым.
- **Синхронизация копий после правки** → контроль уже встроен:
  `sync-release.ps1` сверяет копии с эталоном и падает с exit 1.
- **`gh release edit` не меняет сообщение уже созданного тега** → у
  редактируемых релизов тело релиза и тело тега могут расходиться;
  переписывание тегов = переписывание истории, вне скоупа (требование
  «тег == тело» остаётся действующим для новых релизов).
- **Два корневых источника правила (docs и AGENTS-блок) рассинхронизируются**
  → правятся в один заход, синхронность держит sync-сверка копий.

## Migration Plan

1. Эталоны-документы: `docs/versioning.md` (формат-контракт + исторические
   секции), `docs/agents-versioning-block.md` и блок корневого `AGENTS.md`
   (правило писать блок в момент работы), один пункт в `CHANGELOG.md` корня.
2. `scripts/release.ps1`: структурный гейт на месте `:217`, классификатор
   по жирным меткам, `$SCRIPT_VERSION` → 1.4.0;
   `tests/test_release_phases.py`: фикстуры прозы / длинной строки / кавычек /
   блока без буллетов → отказ без записей; валидный блок → успех;
   секция только с `**Исправлено**` → PATCH.
3. `sync-release.ps1 -LocalOnly -Apply`, затем `sync-release.ps1 -Apply`;
   коммиты рассылки — по команде владельца.
4. FogMap: блоки трёх секций, коммит удалённого дубля, `gh release edit
   --notes-file` ×3, визуальная сверка страниц релизов.
5. instagram-tracker: верхний блок `[Unreleased]`.
6. Сверка: `openspec validate`, `python scripts/check-version.py --all`,
   `sync-release.ps1` (план сверки копий), прогон `tests/test_release_phases.py`.

Откат: revert коммита `release.ps1` + повторный sync (копии вернутся к 1.3.0),
тот же revert для доков; тела релизов возвращаются `gh release edit
--notes-file` прежним текстом из git-истории changelog.

## Open Questions

- Проверка формата блока в `check-version.py` (`--all` из корня): ловить
  нарушение контракта во всех 12 проектах одной командой до релиза. Не
  меняет ни спек, ни скоупа (гейт уже покрывает поведение), поэтому
  откладывается — кандидат в отдельный change после накопления опыта гейта.
