# Design: show-whats-new-on-app-pages

## Context

Мотивация — в proposal.md (раздел Why). Здесь — только то, что нужно для выбора реализации.

`generate.py` уже запрашивает `GET /repos/<repo>/releases/latest` (`fetch_latest_release`, строка 140) и складывает в карточку данные релиза через `release_card()` (строка 154): версия, суммарный размер, дата, счётчик, ссылка `html_url`, список ассетов. Поле `body` в ответе API есть, но сейчас отбрасывается. Страница приложения рендерится из `APP_TEMPLATE` (строка 719) подстановкой `{description}`, `{requirements}`, `{notice}`, `{gallery}` — все блоки формируются отдельными функциями и вставляются как готовый HTML.

Тело релиза публикует release-скрипт приложения из секции changelog (`Get-ReleaseNotes` в `scripts/release.ps1`, строка 153): текст до первой строки `###` — то есть только пользовательский блок (жирные метки категорий + буллеты, ≤140 символов, без `` ` ``). У исторических релизов, опубликованных до введения формат-контракта, в теле может быть свободная проза или вся секция целиком. Стор приложений не знает: читает только публичный GitHub API.

## Goals / Non-Goals

**Goals:**
- Показать краткий блок изменений последнего релиза на странице скачиваемого приложения, без новых обращений к API.
- Корректно отрендерить оба реальных формата тела: контрактный (метки + буллеты) и исторический (проза).
- Полная безопасность разметки: тело релиза — данные внешнего источника, экранирование обязательно.

**Non-Goals:**
- История релизов (только последний; дальше — ссылка «Все изменения» на страницу релизов).
- Чтение `CHANGELOG.md` репозитория и показ ещё не опубликованного `[Unreleased]`.
- Поддержка полного markdown (ссылки, код, наклонный/жирный внутри строки) — контракт блока его запрещает, исторические релизы показываем как есть.
- Секция на карточках главной и на страницах веб-приложений.
- Изменение контракта потребителей (`store.yaml`, `version`, ассеты) — не требуется.

## Decisions

### D1. Источник — `body` из уже существующего запроса
`release_card()` добавляет поле `notes`: `release.get("body") or ""`. Альтернатива (отклонена): парсить `CHANGELOG.md` через raw API — второй запрос на проект, свой парсер секций и дубль логики release-скрипта; плюс показывал бы `[Unreleased]`, которого ещё нет в релизе. Тело релиза — публикованное, проверенное гейтом формат-контракта, и уже подхватывается витриной по событию/cron наравне с версией.

### D2. Мини-парсер тела: один проход, три типа строк
Функция рендера тела проходит строки и классифицирует:
- строка целиком вида `**Метка**` → `<h3 class="wn-label">Метка</h3>` (маркеры `**` снимаются, текст экранируется);
- строка начинается с `- ` → элемент `<li>`; подряд идущие буллеты собираются в один `<ul>`;
- всё прочее (непустые строки) → `<p>`; пустые строки — разделители, игнорируются.

Альтернатива (отклонена): подключить markdown-библиотеку — противоречит «Python без фреймворков» и принципу минимализма; полный markdown контрактом запрещён, нужен ровно этот узкий формат. Инлайновая разметка внутри строки (`**жирный**`, `_курсив_`, `[ссылка]`) не поддерживается и выводится как видимый текст — это безопаснее, чем пытаться отгадывать.

### D3. Разметка секции и положение
```
<section class="whats-new">
  <h2>Что нового в {version}</h2>
  {тело: h3/ul/p}
  <p class="sources"><a href="https://github.com/{repo}/releases">Все изменения</a></p>
</section>
```
Секция вставляется в `APP_TEMPLATE` плейсхолдером `{whats_new}` между `{requirements}` и `{gallery}` — ровно позиция, выбранная владельцем. Ссылка «Все изменения» ведёт на страницу релизов репозитория (`/releases`), а не на конкретный релиз: посетителю интересна история целиком, а `html_url` конкретного релиза дублирует уже показанную версию.

### D4. Пустое тело — секция не выводится
Пустая строка или `None` → функция возвращает `""`, шаблон подставляет пустую строку — страница идентична нынешней. Web-карточки секции не касаются: у них нет релизов, и `{whats_new}` в их шаблон не попадает. Падений и предупреждений — ноль, в духе «skip + warning» витрины.

### D5. Оформление
CSS-блок `.whats-new` рядом с `.gallery` на токенах темы (`--surface`, `--border`, `--sp-*`, `--fs-*`) — карточка-поверхность в стиле `.requirements`, но со списком. Контраст текста и ссылки — AA в обеих темах (требование «Доступность оформления и анимации»); анимации не нужны, `prefers-reduced-motion` не затрагивается.

## Risks / Trade-offs

- [Исторический релиз с длинной прозой даст тяжёлую секцию] → допустимо: страница статическая, секция идёт ниже описания; контрактные релизы ограничены ≤140 символами на строку. Резать автоматически — нет, искажение текста владельца хуже длинного блока.
- [Инлайновая разметка старых тел выводится звёздочками] → осознанный trade-off: безопасность и простота важнее косметики на нескольких исторических релизах; новые релизы по контракту её не содержат.
- [Тело релиза меняется владельцем приложения вне гейта (ручной редакт через UI)] → экранирование нейтрализует разметку; в худшем случае секция покажет неказистый, но безопасный текст.
- [Пустое тело у релиза старше контракта] → секция просто отсутствует, страница не меняется.

## Migration Plan

Деплой — штатный: коммит → cron/событийная сборка → GitHub Pages. Откат — revert коммита, статика возвращается к прежнему виду без миграций данных. Старые релизы не перепубликовываются: парсер терпимо читает их тела как есть.
