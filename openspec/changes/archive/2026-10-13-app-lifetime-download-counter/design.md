## Context

Витрина собирает карточку из `fetch_latest_release()` → `release_card()`. `downloads` сейчас выводится как `sum(download_count ассетов)` единственного релиза из `releases/latest` (`generate.py:167`). GitHub хранит `download_count` в разрезе ассетов релиза, поэтому каждая новая версия стартует с нуля. Нужно: счётчик = сумма по всем опубликованным релизам приложения (привязка к приложению), при этом версия/размер/дата/ссылки/«Что нового» остаются из `releases/latest`. Мотивация — в proposal.md.

Инварианты каталога (не ломаем): битый/недоступный источник → skip + warning, сборка не падает; проект без релиза или без ассетов скрыт. Токен `GITHUB_TOKEN` уже пробрасывается в `github_api()` опционально.

## Goals / Non-Goals

**Goals:**
- `downloads` карточки и страницы = сумма `download_count` по всем **опубликованным** релизам репозитория (include prerelease, exclude draft).
- Счёт не обнуляется при выходе новой версии.
- Версия/размер/дата/ссылки/«Что нового» — без изменений, из `releases/latest`.
- Сборка не падает при сбое получения списка релизов; счёт деградирует предсказуемо.

**Non-Goals:**
- Менять контракт данных приложений (`store.yaml`) или способ публикации релизов источников.
- Считать скачивания вне GitHub Releases (у стора нет иного источника).
- Вводить отдельное хранилище счётчика (счёт всегда из GitHub API, а не из `store.yaml` — `store-data-contract`).

## Decisions

**D1. Источник суммы — пагинированный `GET /repos/{repo}/releases`.**
Новый helper `fetch_all_releases(repo, token)`: обход `?per_page=100&page=N` до короткой страницы либо до лимита страниц (`MAX_RELEASE_PAGES = 10`, т.е. до 1000 релизов). Фильтр: пропускать `draft == True`; брать всё остальное, включая prerelease.
- Альтернатива (отклонена): вычислять сумму из `releases/latest` — невозможно, там один релиз.
- Альтернатива (отклонена): `?per_page=100` без лимита страниц — repo с сотнями релизов раздувает сборку; лимит даёт верхнюю границу вызовов.

**D2. Суммирование — отдельный helper `sum_download_count(releases)`.**
Чистая функция: по списку релизов суммирует `download_count` их ассетов, возвращая вызывающему только итоговое число. Логика фильтра draft живёт в `fetch_all_releases` (отбор релизов), а не в суммировании.

**D3. Связка с latest: `release_card()` принимает готовое `downloads` отдельно от `release`.**
Цикл в сборе каталога (около `generate.py:280`) после получения `release` дополнительно зовёт `fetch_all_releases`, считает `sum_download_count` и передаёт `downloads` в `release_card` (или кладёт в card после). Так версионные поля по-прежнему из latest, а счёт — из агрегата.
- Замечание (осознанная разница scope): `releases/latest` возвращает последний **stable** (GitHub исключает prerelease), а сумма включает скачивания prerelease. Это deliberate: версия = последний стабильный релиз, счётчик = за всё время приложения. Карточка от этого не падает и не противоречит спеке.

**D4. Отказ получения списка релизов → fallback на счёт последнего релиза + warning.**
Если `fetch_all_releases` упал (ошибка сети/JSON/лимит), берём `downloads` из `release` (текущее best-effort поведение) и печатаем `[WARN]`. Это согласуется с инвариантом «витрина не падает» и не прячет проект из-за временного сбоя агрегирующего запроса.
- Альтернатива (отклонена): скрывать проект при сбое списка — слишком жёстко: витрина теряет карточку из-за доп. запроса.

**D5. Токен.** Сумма требует больше запросов к API; без токена лимит 60/ч, с токеном 1000/ч. Токен уже опционально пробрасывается. В CI (GitHub Actions) `GITHUB_TOKEN` доступен — на cron-расписании (≤30 мин) добавленные вызовы укладываются в лимит и без токена, но токен предпочтителен. Новых секретов не вводим.

**D6. Тесты** (`tests/test_generate.py`): обновить фикстуру (сейчас один релиз → `downloads == 7`). Добавить кейсы: (a) несколько релизов → сумма; (b) prerelease включён, draft исключён; (c) fallback при пустом/битом ответе списка; (d) граница лимита страниц.

## Risks / Trade-offs

- [Больше запросов к GitHub API → риск rate limit] → лимит страниц (D1), токен в CI (D5); при сбое — fallback на счёт latest (D4), сборка не падает.
- [Версия (latest stable) и счёт (сумма с prerelease) — разный scope] → осознанно (D3); оба честны в своём смысле, карточка консистентна.
- [Draft-релизы могут попасть в список при токене с push-доступом] → явный фильтр `not draft` (D1) — их скачивания не считаются.
- [Репозиторий с очень большим числом релизов] → срез по `MAX_RELEASE_PAGES`; выше порога сумма становится приближением — приемлемо, т.к. реальные проекты имеют единицы/десятки релизов.

## Migration Plan

Деплой — обычная сборка витрины CI (cron/событие). Изменение идёт в одном релизе витрины: после публикации карточки сразу показывают накопленный счёт. Откат — revert коммита генератора; состояние не мигрируется (счёт всегда пересчитывается из GitHub API, сохранённого состояния нет).
