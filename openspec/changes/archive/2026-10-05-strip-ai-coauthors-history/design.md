# Design: strip-ai-coauthors-history

## Context

Аудит 11 репозиториев владельца (критерий — строка, начинающаяся с
`Co-Authored-By:` или `Generated with`) выявил нарушения в 6 ветках по
умолчанию: `InstagramTracker` 22/20, `VoiceMind` 9/7, `GymProgress` 2/2,
`ChargeForecast` 2/2, `FogMap` 1/0 (соавтор `opencode`), `PersonalData` 2/2
(в первом числе — `Co-Authored-By:`, во втором — `Generated with`).

Пять репозиториев чисты. `Benchmark` в HEAD не имеет трейлеров, но в локальных
рефах `refs/cascades/*` (54 коммита вне HEAD, на `origin` не выгружены) — 10
`Co-Authored-By:` и 11 `Generated with`. `PersonalData` имеет 2 локальных
коммита вне HEAD без трейлеров.

Правило уже сформулировано в `.devin/rules/git.md` репозитория Benchmark —
включая формулировку критерия «строки, начинающиеся с `Generated with` или
`Co-Authored-By:`». Ни одна из спек корня формат коммитов не покрывает;
переписывание истории не меняет ни одного их требования, поскольку дерево
коммитов остаётся тем же (см. proposal.md — Why).

Условия, данные на момент планирования: все клоны чисты и синхронизированы
(0 ahead / 0 behind), открытых PR нет, защищённых веток нет, 7 тегов —
аннотированные, под каждым тегом есть GitHub Release.

## Goals / Non-Goals

**Goals:**

- История веток по умолчанию 6 репозиториев не содержит агентских трейлеров.
- Теги и релизы продолжают указывать на те же версии с теми же деревьями.
- Правило запрета трейлеров живёт в корне и доступно каждому проекту
  самостоятельно.
- Существует локально запускаемая проверка, находящая нарушения по всем
  проектам владельца.

**Non-Goals:**

- Пересборка или перепубликация ассетов релизов.
- Запрет коммитов без явного указания пользователя и запрет push без
  указания — эти правила Benchmark остаются как есть и не поднимаются в корень.
- Приведение в порядок содержимого `refs/cascades/*` (снимки) — меняется только
  их сообщение коммитов, назначение рефов не трогается.
- Внедрение проверки в CI — см. Open Questions.
- Правка истории репозиториев, где нарушений в HEAD нет.

## Decisions

### D1. Инструмент — `git filter-repo`, не `filter-branch` и не `rebase`

Альтернативы: `git filter-branch` (выводит собственное предупреждение
«has a glut of gotchas generating mangled history», медленный, ручная
обработка сообщений), интерактивный `rebase` (34–116 коммитов на репо,
ручной проход по каждому, ошибка на коммите = переигрывание всей последовательности).

`git-filter-repo` декларативно правит сообщения по всем рефам за один проход,
сохраняет автора, даты и деревья, корректно переносит теги. Инструмент не
установлен — ставится `pip install git-filter-repo` (`python` и `pip` в системе
есть). Проверенное поведение: отказ работать в несвежем клоне → флаг `--force`,
и удаление `origin` после прогона → URL репозитория фиксируется заранее и
remote добавляется обратно до выгрузки.

### D2. Критерий — начало строки, а не любое упоминание

Фильтр: `(?m)^\s*Co-[Aa]uthored-[Bb]y:\s+\S` и `(?m)^\s*Generated with`.
Почему не «любое вхождение»: в `Benchmark` есть 2 коммита, *описывающих* запрет
(`rules: prohibit Generated with [...] and Co-Authored-By in commits`) — они
упоминают запрет внутри предложения и не являются трейлерами. Критерий
«начало строки» взят дословно из действующего правила Benchmark и покрывает
битую форму `Co-Authored-By: Devin <...noreply.github.com` (без закрывающей `>`)
в `VoiceMind`, где строка всё равно начинается с трейлера.

Регулярка регистронезависима к `Co-Authored`/`Co-authored`, т.к. в истории
обе формы.

### D3. Объём переписывания — только репозитории с нарушениями в HEAD

Переписываются `InstagramTracker`, `VoiceMind`, `GymProgress`, `ChargeForecast`,
`FogMap`, `PersonalData`. Остальные 5, включая `Benchmark` (HEAD чист), не
получают ни перезаписи, ни force push — их история и хеши остаются прежними.

Локальные `refs/cascades/*` в `Benchmark` и `PersonalData` входят в прогон
(иначе `git log --all` продолжит показывать трейлеры), но на `origin` не
выгружаются — для них force push не требуется.

### D4. Ветки и теги выгружаются одним форс-пушем

После прогона: `git push --force --follow-tags origin --all` — ветка по
умолчанию и аннотированные теги уходят вместе. GitHub привязывает Release к
тегу, а не к хешу, поэтому релизы и их ассеты переходят на новые хеши
автоматически и пересоздавать их не нужно. Проверка после выгрузки — что под
тегом лежит коммит с ожидаемой секцией `CHANGELOG.md` в дереве.

### D5. Бэкап-клон до прогона

`git clone --mirror <url> <имя>.bak` в отдельную папку до переписывания.
Единственная возможность отката: старые хеши после `--force` не восстанавливаются,
поэтому бэкап — не оптимизация, а условие запуска (см. spec: «очистка MUST
признаваться необратимой»). Бэкапы не удаляются до завершения проверки.

### D6. Правило и проверка — в корне, доставка — через `AGENTS.md`

Правило переносится из `.devin/rules/git.md` Benchmark в корень как эталон;
в каждый проект — копия в `AGENTS.md`, IDE-нейтральном always-on источнике
(так уже устроено в `GymProgress`: «Единый IDE-нейтральный источник always-on
правил»). Копии в `.devin/`/`.cursor/`/`.opencode/` конкретного проекта
остаются, если там есть — противоречить эталону не должны.

Проверка — скрипт в `scripts/` корня рядом с существующим
`scripts/check-version.py`, по той же модели вызова (`--all`, `--project KEY`)
и кодам выхода (0 — чисто, 1 — нарушение). Список проектов и их локальные пути
берутся из `versioning.yaml` — того же файла, который уже читает
`check-version.py` (`import yaml`, поля `projects.*.path`, `repo`, `git`).
Это соответствует принятому правилу «корень знает обо всех проектах»
и не заставляет проекты хранить знания друг о друге; `registry.yaml` для этой
цели не подходит — он описывает только состав витрины, без локальных путей и
без признака `git: false` (как у `tempproject`, где git отсутствует в принципе).

### D7. Changelog не пополняется

Перезапись истории и подъём правила — внутренняя работа и доки; по правилу
корня «чистые доки, спеки, тесты, CI и внутренний рефактор в changelog не
пишутся», а версия статического трека заморожена. `check-version.py` до и
после должен оставаться exit 0.

## Risks / Trade-offs

- **Внешние ссылки на старые хеши перестают работать** (закрытые PR, форки,
  выложенные логи) → принимается сознательно; перед прогоном фиксируется
  список старых хешей HEAD, бэкап-клон хранит полную историю.
- **`filter-repo` удалит `origin` после прогона** → URL репозитория
  записывается до запуска, remote добавляется обратно до выгрузки; выгрузка
  идёт только после успешной проверки.
- **GitHub кэширует список contributors** → после выгрузки проверка через API
  может показывать ботов ещё некоторое время; окончательная сверка — повторным
  запросом, расхождение не считается дефектом очистки.
- **`--follow-tags` не захватит теги, не достижимые из веток** → перед прогоном
  фиксируется список всех тегов, после — сверяется, что каждый тег существует
  и указывает на коммит с нужным деревом.
- **Грязное рабочее деревое блокирует прогон** → условие запуска: все 11
  репозиториев чисты и синхронизированы (на момент планирования выполнено).
- **Трейлеры вернутся, если правило останется только в Benchmark** → D6:
  эталон в корне + копия в `AGENTS.md` каждого проекта + проверка в корне.
- **Локальные рефы `refs/cascades/*` изменят хеши** → это снимки, они не
  выгружены и не участвуют в релизах; содержимое деревьев сохраняется.

## Migration Plan

1. Сверка условий: чистота всех клона, синхронизированность, список тегов и
   хешей HEAD, установка `git-filter-repo`.
2. Бэкап-клон `--mirror` для 6 репозиториев.
3. Прогон по сообщениям во всех рефах, локальная проверка (0 трейлеров в
   `git log --all`).
4. Force push веток и тегов, восстановление `remote.origin.url` если удалён.
5. Сверка: теги → коммиты с теми же деревьями, релизы на месте, `check-version.py`
   exit 0, проверка коммитов exit 0, повторный запрос contributors через API.
6. Откат невозможен из remote — только из бэкап-клона, до шага 4 включительно.

## Open Questions
