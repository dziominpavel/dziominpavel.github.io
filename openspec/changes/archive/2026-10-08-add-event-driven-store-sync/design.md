# Design: add-event-driven-store-sync

## Context

Мотивация и объём — в `proposal.md` (Why / What Changes). Здесь — только то, что определяет подход.

Наблюдения, влияющие на решения:

- Сборка витрины **полная и идемпотентная**: `generate.py` на каждом запуске клонирует все репозитории и перечитывает `releases/latest` (`generate.py:256-292`). Инкрементальности и кэша нет → payload события витрине не нужен, ей нужно только «запусти сборку».
- `build.yml` уже содержит `concurrency: group: pages-build, cancel-in-progress: true` и job `deploy`, `needs: build` → событийный запуск автоматически деплоит и, при параллельном cron-запуске, отменяет устаревший.
- cron фактически даёт 8 запусков за 3 дня (провалы до 7 часов) → расписание остаётся, но не может быть основным каналом.
- Токен владельца `gho_…` со scope `repo` (проверено `gh auth status`) — релизный хук **не требует новых секретов**; endpoint `POST /repos/{owner}/{repo}/dispatches` в документации требует ровно `repo` у OAuth/classic-токена.
- У 6 из 7 репозиториев приложений и у обоих web-источников (`Benchmark`, `InstagramTracker`) — **0 workflows**; у `FogMap` есть `ci`.
- `release.ps1` — единственный эталон, разносится `sync-release.ps1` удалённым каналом и контролируется финальной сверкой (`exit 1` при расхождении).

## Goals / Non-Goals

**Goals:**
- Сборка витрины запускается по событию (релиз приложения / пуш web-статики) и не зависит от расписания.
- Единый релизный хук действует во всех 7 репозиториях без ручной раздачи.
- При любом сбое нового канала витрина продолжает обновляться по cron — деградация, а не отказ.

**Non-Goals:**
- Менять `generate.py`, контракт данных, содержимое страниц или частоту требования cron «не более 30 минут».
- Инкрементальная сборка, кэш данных релизов, передача payload в генератор.
- Клиентская сверка версий на странице (слой 4) — отложено как отдельное изменение.
- Триггерить витрину по всем коммитам приложений: по контракту её данные меняет только релиз.

## Decisions

### D1. Канал событий — `repository_dispatch`, а не alternatives
Выбран `repository_dispatch` с типами `app-released` и `web-updated`.

Альтернативы:
- **`workflow_dispatch`** — работает с тем же токеном, но запускает конкретный workflow без семантики события: типы событий не понадобятся, а расширение (новый источник) придётся логировать «руками». `repository_dispatch` — штатный механизм «событие снаружи → workflow».
- **Полегчить cron (чаще `*/30`)** — не устраняет причину: теряются именно запуски, а не интервалы; решение остаётся ненадёжным.
- **Push-канал «приложение коммитит в витрину»** — потребует токена с записью в витрину у каждого источника (шире, чем токен на чтение-оповещение) и мусорных коммитов в `main`.
- **GitHub App / свой обработчик вебхуков** — требует внешней инфраструктуры, противоречит требованию «всё бесплатно, без сторонних сервисов».
- **Клиентская сверка версий на странице** — снимает зависимость от CI только для видимых полей, но меняет спеки `store-catalog`/`store-data-contract` и упирается в rate limit unauthenticated API; отложено.

Payload события **не используется**: сборка полная, а лишние данные в логе не нужны. `client_payload` ограничивается `{repo, tag}` только для трассировки в логах Actions (лимит — 10 top-level свойств, 64 KB — с запасом).

### D2. Релизный хук — в `release.ps1`, фаза 10, после `gh release create`
Хук добавляется в эталон скрипта, **после** успешной публикации и **до** `exit 0`. Публикация `gh release create $Tag @Staged ...` возвращает ответ только после загрузки всех ассетов, поэтому к моменту оповещения релиз полностью виден API — гонки «витрина собрала релиз без ассетов» нет.

Почему скрипт, а не workflow в каждом репозитории:
- один эталон + существующий механизм разноса (`sync-release.ps1`, удалённый канал) и финальная сверка копий — вместо 7 одинаковых workflow;
- ноль новых секретов: работает уже авторизованный `gh` владельца;
- alternative с `on: push: tags: v*` срабатывает **до** публикации релиза (тег пушится раньше `gh release create`), что создаёт гонку, и всё равно требует PAT в каждом репо.

Обработка сбоя: `try/catch` → `[WARN]`, код возврата скрипта остаётся `0`. Релиз опубликован — валить его из-за оповещения нельзя. Секция спеки «Оповещение витрины о релизе» фиксирует это как контракт.

### D3. Токен для web-источников — секрет `STORE_DISPATCH_TOKEN` (classic PAT, scope `repo`)
`GITHUB_TOKEN` workflow репозитория-источника **не подходит**: он выдаётся только для собственного репозитория и не имеет доступа к витрине. Значит, секрет обязателен.

- Выбран classic PAT со scope `repo` — документированное для `repository_dispatch` требование. Fine-grained токен в документации для этого endpoint явно не указан, поэтому на него не полагаемся (см. Open Questions).
- Один и токен-значение в два репозитория (`Benchmark`, `InstagramTracker`) — проще ротация.
- Секрет заводит владелец вручную; без него webhook-часть просто не работает, а витрина продолжает обновляться по cron (см. Risk).

Альтернатива — вообще не делать слой для web и оставить web-карточки на cron: отклонена, потому что именно web-данные (`data/index.json`, `web/`) меняются вне релизного цикла и на cron не подхватываются ничем другим.

### D4. Workflow источника — `on: push: paths`, первый workflow в этих репо
Для каждого web-источника создаётся `.github/workflows/notify-store.yml`:

- `Benchmark`: `paths: [web/**, data/**]` (по `registry.yaml` у него объявлен `data: data/index.json`);
- `InstagramTracker`: `paths: [web/**]` (он же скачиваемый проект — релизный хук приходит отдельно из `release.ps1`).

Один шаг: `gh api -X POST .../dispatches -f event_type=web-updated` с `GH_TOKEN: ${{ secrets.STORE_DISPATCH_TOKEN }}` (`gh` уже предустановлен на runner). `permissions: contents: read` — минимально необходимые права самому job'у.

Фильтрация «а изменилось ли что-то значимое» не делается: лишняя сборка идемпотентна и занимает ~1 минуту.

### D5. Второй слот расписания — включаем
Кроме `*/30` добавляется `17,47 * * * *`. Аргументы: страховочный канал — единственный защитный механизм от промахов оповещений, а наблюдаемая частота запусков в ~15 раз ниже номинальной, поэтому удвоение слотов почти не увеличит реальную нагрузку (≤7 API-запросов на сборку при лимите 5000/час). Откат — удаление одной строки.

Отклонено: третий и дальнейшие слоты (предельная отдача нулевая), и отклонено оставление одного `*/30` — оставляет страховку такой же ненадёжной, какой была основная причина изменения.

## Risks / Trade-offs

- **[PAT в секретах публичных репозиториев]** → форки и PR из форков секрет не получают; workflow срабатывает только на push в `main` (владелец); при подозрении на компрометацию — ротация PAT и замена значения в двух секретах. Следствие D3.
- **[PAT истёк или отозван]** → оповещения web-источников молча перестают работать, витрина отстаёт до cron-запуска. Митигация: предупреждение в логе workflow, cron-подстраховка, место хранения секрета описано в README.
- **[Release-скрипт не обновлён в части репозиториев]** → молча не будет оповещений у этих проектов. Митигация: `sync-release.ps1` в финале всегда сверяет копии с эталоном и выходит с `exit 1`; cron.
- **[Оповещение отправлено, но сборка витрины упала]** → run виден в Actions со статусом; витрина остаётся на предыдущей версии до следующего успешного запуска (cron или событие). Новых классов отказа не добавляем — сборка и раньше могла упасть.
- **[Ложное срабатывание: пуш не меняет данные витрины]** → лишняя идемпотентная сборка ~1 минута. Приемлемо против сложности фильтрации.
- **[Релиз опубликован минуя скрипт]** → оповещения нет, обновление ждёт cron. Явно описано в спеке как ожидаемое поведение.
- **[GitHub отключит cron при 60 днях неактивности репозитория]** → витрина активно пушится (изменения `registry.yaml`, шаблонов, скриптов), событийный канал от cron не зависит.

## Migration Plan

1. **Корень**: `build.yml` — блок `repository_dispatch` и второй cron-слот; push → сборка зелёная (`tests/test_generate.py`, `tests/test_release_phases.py`, `validate_site.py`).
2. **Корень**: хук в `scripts/release.ps1` + бамп `$SCRIPT_VERSION`; юнит-тесты фаз; пункт в `CHANGELOG.md` → `## [Unreleased]`.
3. **Разнос**: `sync-release.ps1 -Apply` — удалённый канал обновляет `release.ps1`/`release.bat` в 7 репозиториях; завершение с `[OK]` (сверка копий) обязательно.
4. **Web-источники**: создать `notify-store.yml` в `Benchmark` и `InstagramTracker` (через `gh api` contents) и **вручную** завести секрет `STORE_DISPATCH_TOKEN` в обоих.
5. **Проверка end-to-end**: ручной `gh api .../dispatches` → run с `event=repository_dispatch` → витрина показывает актуальные данные; затем push в `web/` одного из источников → тот же путь.
6. **Релиз-путь**: первый реальный релиз любого приложения (или `release.ps1` в песочнице) подтверждает, что оповещение уходит и релиз не пострадал при сбое.

Rollback: revert блоков в `build.yml` (событийные вызовы перестают запускать workflow, витрина остаётся на cron) + удаление workflow/секрета в web-источниках. Хук в `release.ps1` откатывается тем же revert + повторным `sync-release.ps1 -Apply`; на релизы откат не влияет — оповещение best-effort.

## Open Questions

- **Fine-grained PAT вместо classic** — если при ручном заведении токена fine-grained с `contents: write` на репозитории витрины сработает с `repository_dispatch`, сузим секрет. Не меняет спеки, подход и план задач — меняет только значение секрета; проверяется тем же ручным dispatch из шага 5 миграции.
