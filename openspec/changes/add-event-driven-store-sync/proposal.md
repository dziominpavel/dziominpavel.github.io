# Proposal: add-event-driven-store-sync

## Why

Синхронизация витрины построена только на cron GitHub Actions, а cron у Actions — best-effort: фактические интервалы между сборками достигали 4–7 часов при расписании `*/30` (наблюдение: `11:57 → 18:50`, за 3 дня — 8 запусков вместо ~144). Из-за этого свежий релиз приложения или коммит web-статики не доходит до витрины часами: `YandexMusicDownloader v0.2.0` опубликован в `19:01`, последняя сборка была в `18:50` — витрина показывает `v0.1.0`. Ручная сборка статики владельцем по контракту MUST NOT требоваться, поэтому единственный надёжный способ — перестать полагаться на расписание и пересобирать витрину по событию.

## What Changes

- Витрина получает **событийный триггер** `repository_dispatch` с типами `app-released` и `web-updated`: сборка запускается сразу после публикации релиза приложения или коммита, тронувшего web-статику, без ожидания cron.
- **Release-скрипт** (единый эталон в корне, разносится `sync-release.ps1` в 7 репозиториев) после успешной публикации релиза best-effort оповещает витрину: сбой оповещения MUST выдаваться как предупреждение и MUST NOT завершать релиз ошибкой и MUST NOT откатывать тег.
- **Репозитории-источники web-приложений** (`Benchmark`, `InstagramTracker`) получают первый workflow, который оповещает витрину о пуше, тронувшем `web/**` (и `data/**` у Benchmark). Для межрепозиторного вызова вводится один секрет-токен, заводимый владельцем вручную.
- **cron остаётся подстраховкой** (для релизов, опубликованных мимо скрипта, и промахов токена): расписание не отменяется, ему добавляется второй слот с независимым смещением минут, чтобы страховка чаще попадала в «окно» и не зависела от одного провалившегося запуска.
- Поведение витрины (генерация, контракт данных, содержимое страниц) не меняется — меняется только то, **когда** запускается сборка.

### Modified Capabilities

- `store-catalog`: требование «Автоматическая сборка витрины» дополняется событийными триггерами (`repository_dispatch`) с сохранением cron как подстраховки; сценарий «Опубликован новый релиз» перестаёт быть привязанным к «одному циклу синхронизации» — витрина обновляется по событию, не дожидаясь расписания.
- `app-release-pipeline`: новое требование «Оповещение витрины о релизе» — после публикации release-скрипт инициирует пересборку витрины, не ставя это в зависимость от успешности публикации.
- `store-web-apps`: новое требование «Оповещение витрины об обновлении web-статики» — репозиторий-источник оповещает витрину при пуше, тронувшем статику или файл данных.

## Impact

**Код и конфигурация корневого репозитория:**
- `.github/workflows/build.yml` — блоки `repository_dispatch` и второй cron-слот;
- `scripts/release.ps1` — фаза 10 (после `gh release create`), бамп `$SCRIPT_VERSION`;
- `tests/test_release_phases.py` — покрытие поведения фазы оповещения;
- `README.md` (раздел «Как это устроено»), `CHANGELOG.md` → `## [Unreleased]`.

**Чужие репозитории (через существующие механизмы разноса):**
- `sync-release.ps1 -Apply` — удалённый канал обновляет `release.ps1`/`release.bat` в 7 репозиториях;
- `dziominpavel/Benchmark` и `dziominpavel/InstagramTracker` — создаётся `.github/workflows/notify-store.yml` (у обоих сейчас 0 workflows).

**Внешние зависимости и ручные действия владельца:**
- токен для межрепозиторного вызова: endpoint `POST /repos/{owner}/{repo}/dispatches` требует scope `repo` (текущий `gh`-токен владельца уже имеет его — релизный хук новых секретов не требует);
- секрет `STORE_DISPATCH_TOKEN` в `Benchmark` и `InstagramTracker` заводит владелец вручную: без него web-оповещение не работает, витрина остаётся на cron-подстраховке.

**Не меняется:** `generate.py`, `registry.yaml`, контракт данных приложений, `store-data-contract`, частота cron как требование «не более 30 минут».
