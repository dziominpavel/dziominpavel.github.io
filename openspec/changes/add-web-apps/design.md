## Context

См. proposal.md — Why. Ключевые факты текущего состояния, определяющие подход:

- `generate.py` сам клонирует источники: `clone_project()` делает `git clone --depth 1` репозиторий из `registry.yaml` и при ошибке печатает `[WARN] ... clone не удалён - проект пропущен`, не падая. InstagramTracker и так клонируется; Benchmark нужно добавить.
- `tests/validate_site.py` проверяет **каждый** `*.html` под `_site` рекурсивно: обязательны `charset`, `description`, `og:title`, `viewport`, `favicon`, тексты навигации «Главная» и «О проекте», подключение `static/js/theme.js` (подстрока), `lang="ru"`, `data-theme="dark"`, корректная вложенность тегов и отсутствие литералов `{word}`. Sitemap сравнивается с множеством `index.html` **точным равенством** — каждый опубликованный `index.html` обязан иметь свой `<loc>` и наоборот.
- Контракт скачиваемых приложений (release-данные, скриншоты, version) в этом изменении не трогается; веб-записи живут в отдельной секции реестра и в отдельной capability.

## Goals / Non-Goals

**Goals:**

- Единый origin: веб-приложения живут на `dziominpavel.github.io/apps/<slug>/`, в sitemap, с навигацией в каталог.
- Нулевые внешние зависимости: без CDN, без бэкенда, без платных сервисов; сборка устойчива (skip + warning при битом источнике).
- Приватность Instagram-анализера: данные экспорта ни при каких условиях не покидают браузер посетителя.
- Benchmark — строго read-only статика из `index.json`, обновляемая только при сборке витрины.
- Все web-страницы проходят существующий `validate_site.py` без ослабления тестов.

**Non-Goals:**

- iframe-оверлей/полноэкранный «запуск внутри витрины» — вместо него полноценные страницы (см. D2).
- PWA/offline, service workers, авторизация, любые формы отправки данных.
- Публикация содержимого `answers/`, `matchups/`, логов Benchmark — только агрегаты из `index.json`.
- Web-версии остальных проектов (YandexMusicDownloader и др.).
- Единый дизайн-фреймворк для веб-приложений: у каждой страницы свой CSS, но служебный каркас витрины обязателен (D3).

## Decisions

### D1. Источник статики: папка `web/` в репозитории-источнике, копирование внутри `generate.py`

Веб-приложение живёт в своём репозитории как `web/` (вход — `web/index.html`). `generate.py` переиспользует существующий `clone_project()` для каждой web-записи (Benchmark — новый клон, InstagramTracker — уже клонируется) и копирует `web/` в `_site/apps/<slug>/`, а для Benchmark дополнительно рядом — `data/index.json`. Успех копирования определяет всё: карточку на главной, URL в sitemap и саму страницу (требование спеки «источник недоступен → skip + warning» и «sitemap — точное равенство» выполнимы только из одного источника истины). Ошибка клонирования/отсутствие `index.html` → `[WARN]` в лог, без карточки и без URL, сборка продолжается — это уже готовое поведение `clone_project()`.

*Альтернативы:* raw-fetch файлов через GitHub API — отклонено (хрупко для набора из нескольких файлов); коммит статики в стор-репо — отклонено (контент живёт вдали от источника, `index.json` Benchmark всё равно надо тянуть по сети); шаг клона в CI workflow — отклонено (логика skip/карточка/sitemap атомарно живёт в генераторе, workflow не умеет решать, что показывать).

### D2. Страницы, а не iframe-оверлей

`/apps/<slug>/` — обычная страница витрины (само приложение и есть `index.html` папки). Обсуждавшийся iframe-оверлей («приложение внутри витрины») отклонён: он ломает адресацию/бэк/шаринг, добавляет проблемы с базовыми путями и скроллом, а требование «открывается отдельно» закрывается собственным URL. Навигацию «назад» и служебные маркеры витрины несёт контракт источника (D3) — каждый посетитель получает «Главная», «О проекте» и переключатель темы.

*Альтернативы:* iframe-обёртка из шаблона генератора (шапка витрины + `<iframe>` → `app/index.html`) — отклонено: двойная адресная строка на мобиле, косвенность, вложенные `index.html` ломают точное равенство sitemap; инъекция шапки в HTML источника генератором — отклонено (хрупкий парсинг чужого HTML).

### D3. Контракт web-источника

Запись в `registry.yaml`:

```yaml
web:
  benchmark:
    repo: dziominpavel/Benchmark
    title: Benchmark
    description: "ELO-рейтинг LLM-моделей: ..."
  instagram-tracker:
    repo: dziominpavel/InstagramTracker
    title: InstagramTracker Web
    description: "..."
```

Файловый контракт папки `web/` источника: `index.html` (вход) + ресурсы; обязательный служебный каркас, чтобы страница проходила `validate_site.py`:

- `<html lang="ru" data-theme="dark">`, `charset=utf-8`, `meta description`, `og:title`, `viewport`, `link rel="icon"`;
- nav со ссылками «Главная» (`../../`) и «О проекте» (`../../about/` — путь сверяется с реальной страницей «О проекте» при реализации);
- подключение `static/js/theme.js` относительным путём (`../../static/js/theme.js`) **в `<head>` до подключения стилей** — выполняется до первой отрисовки (нет вспышки светлой темы) и подключает обработчик `#theme-toggle`; иконка-кнопка темы — по желанию, но маркер подключения обязателен;
- отсутствие литералов вида `{word}` в коде (ловушка leftover-проверки валидатора).

Карточка: `title`, `description`, иконка — из `web/icon.png` источника (опционально; нет → буквенный плейсхолдер по правилу store-catalog); дата обновления — `index.json:updated` для Benchmark, иначе дата сборки витрины.

### D4. InstagramTracker Web: анализер, порт 82-строчного парсера, всё локально

Одностраничник в `web/` репозитория instagram-tracker: инструкция (3 шага: куда зайти → что выгрузить → куда загрузить) → зона drag&drop → дашборд. Разбор на JS: порт `app/parser.py` один-в-один (паттерны `followers_*.json`, `following.json`, `blocked_profiles.json`, `hide_story_from.json`, `recently_unfollowed_profiles.json`, `recent_follow_requests.json`, извлечение username из `label_values`/`string_list_data`, фикс мojibake `latin-1 → utf-8`) + секции из существующего `index.html`/`dashboard_v2.py` как визуальный ориентир. Распаковка ZIP — вендор `fflate` (~8 КБ, MIT) в `web/vendor/`, без CDN; принимаются также папка (`webkitdirectory`-инпут) и отдельные файлы; JSON ищутся рекурсивно внутри дерева ZIP (структура Meta: `connections/followers_and_following/...`). Динамика «новые/потерянные»: снимок (только username-списки и счётчики) сохраняется в `localStorage` (оценка: ~50–100 КБ на снимок при лимите 5 МБ — годится на годы), сравнение с предыдущим снимком; без прошлого снимка — только текущая аналитика. Ошибки разбора — сообщение в зоне загрузки, страница живёт. Никаких `fetch` с данными экспорта (проверяется сценарием приватности).

*Альтернатива:* IndexedDB — отклонено (избыточен для объёмов списков в сотни записей); отправка на «безопасный» сервер — отклонено прямо требованием приватности.

### D5. Benchmark Web: клиентский рендер из `index.json`

`web/index.html` + `web/app.js` в репозитории Benchmark; при сборке рядом копируется `data/index.json`, страница читает его локальным `fetch('index.json')` и рендерит: ELO-таблицу (место, модель, провайдер, рейтинг, В-Н-П, игры), SVG-график динамики рейтингов из `elo_history` (326 записей: по каждой — участники, победитель, дельты), сводку `matchups_summary` и ленту последних прогонов, дату из `updated`. Никаких форм и POST — только чтение; обновление цифр происходит только при сборке витрины (копировании свежего `index.json`).

*Альтернативы:* генерация HTML-графиков в Python на этапе сборки — отклонено (python-чартинг без зависимостей хуже поддерживаем, чем 100 строк рендер-логики на JS рядом с данными); публикация полных данных прогонов — отклонено (приватность/вес: в витрину идёт только агрегатный `index.json`).

### D6. Интеграция с генератором

`generate.py`: чтение секции `web:` (отдельно от release-логика основных проектов), шаг копирования перед рендером, секция «Веб-приложения» на главной **после** сетки скачиваемых (управляется `filter.js` через секцию целиком: видна в сегментах «Все»/«Веб», скрыта под Android/Windows — отдельные web-карточки фильтр поштучно не трогает), URL `/apps/<slug>/` в sitemap только для успешно скопированных. `tests/test_generate.py`: тест на web-запись (успех → карточка+URL; битый источник → skip без падения). `tests/validate_site.py` не ослабляется — его маркеры становятся частью контракта (D3).

## Risks / Trade-offs

- [Сторонний HTML не пройдёт строгие маркеры валидатора] → каркас обязателен по контракту (D3), оба приложения создаём мы сами; гейт — полный прогон `validate_site.py` до push.
- [Литерал `{word}` в JS веб-приложения уронит leftover-проверку] → приём: избегать такого синтаксиса; ловится первым же прогоном валидатора в задачах.
- [Клон Benchmark тяжёлый (data/ с ответами и логами)] → `--depth 1` уже используется; при деградации — sparse-checkout только `web/` и `data/index.json`; clone и так fail-soft.
- [Утечка данных экспорта Instagram через сеть] → запрет `fetch` с данными как контракт; проверка вручную: Network-вкладка при загрузке тестового экспорта (в задачах) — только загрузка статики.
- [sitemap-равенство сломается при частичном успехе] → URL/sitemap/карточка генерируются из результата копирования (D1), не из реестра.
- [Порядок архивации: дельты MODIFIED требуют основных спеков `store-catalog`/`store-data-contract`] → архивировать после `add-app-store` (то же ограничение, что у `redesign-storefront`).
- [Откат] → `git revert` в сторе убирает карточки и страницы; web-статика в репозиториях-источниках безвредна (не публикуется без записи в реестре).

## Migration Plan

1. Репозитории-источники: создать `web/` в InstagramTracker (анализер) и Benchmark (лидерборд), закоммитить и запушить в `master`/`main` соответственно; публикация в стор не происходит автоматически (репозитории об этом не знают — контракт не нарушен).
2. Стор локально: секция `web:` в `registry.yaml` → логика копирования и секция главной в `generate.py` → страницы/sitemap → тесты (`test_generate.py` на web-записи).
3. Гейт: `python generate.py --out _site` → `python tests/test_generate.py` → `python tests/validate_site.py _site` (все web-страницы — OK, sitemap — точное равенство) → браузерная проверка: обе страницы, инструкция и drag&drop анализера на реальном тестовом экспорте, read-only Benchmark, навигация назад, тема.
4. Push стора → CI-деплой → smoke живого сайта (`/apps/benchmark/`, `/apps/instagram-tracker/`, блок на главной).
5. Откат: `git revert` коммита стора → push (страницы и карточки исчезают); при необходимости — revert и в репозиториях-источниках.
6. Архивация изменения — после `add-app-store`.
