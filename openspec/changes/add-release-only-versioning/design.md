# Design: add-release-only-versioning

## Context

См. proposal.md — Why. Ключевые факты текущего состояния, определяющие подход:

- Уже существует единый механизм доставки: `scripts/release.ps1` (побайтово одинаков в 7 репозиториях, `$SCRIPT_VERSION = "1.0.0"`) и `scripts/sync-release.ps1`, разносящий его по `registry.yaml` через GitHub API с фиксацией версии и финальной сверкой всех копий. Канал «эталон в корне → дети» построен и проверен.
- `release.ps1` уже читает файл `version` и отказывается перезаписывать существующий тег, но версию не меняет — её правят руками (или она растёт от сборок).
- В 4 Android-проектах `app/build.gradle.kts` делает `patch += 1` при каждой `assemble`/`install`/`bundle` и считает `versionCode = 2_000_000_000 + major*10000 + minor*100 + patch`. Фактические значения: ChargeForecast `0.1.31` → 2 000 000 131, GymProgress `1.0.634` → 2 000 010 634, VoiceMind `0.1.132` → 2 000 000 232, Wishlot `0.1.28` → 2 000 000 128. При `patch > 99` формула переносит разряд в `minor`, и следующий легитимный бамп (`1.1.0` = 2 000 010 100) даёт значение ниже текущего — обновление отклоняется Android.
- Витрина читает версию только из `releases/latest` (`generate.py:143`), web-записи `registry.yaml` версию не берут вовсе. Промежуточные версии ей недоступны — менять генератор не нужно.
- `FogMap` уже работает по модели «бамп только на релизе» (`docs/versioning.md`, `CHANGELOG.md` с `[Unreleased]`, `scripts/check-version.py`) — это готовый образец, который обобщается на остальные.
- Основные спеки (`openspec/specs/`) пусты: capability `app-release-pipeline`, `store-data-contract`, `store-catalog` существуют пока как дельты активных change (`add-app-store`, `add-web-apps`).
- `registry.yaml` знает 9 из 12 проектов владельца: в нём нет `hours-bridge`, `PersonalData`, `TempProject`. Это каталог витрины, а не перечень проектов.

## Goals / Non-Goals

**Goals:**

- Один предсказуемый цикл: сессии копят `[Unreleased]` → релиз один раз классифицирует и сворачивает → тег.
- Знания о всех проектах — только в корне; дети получают только собственные файлы.
- Первый «серьёзный» бамп в Android-проектах физически возможен (монотонный `versionCode`).
- Рассинхрон «версия в заголовке changelog ≠ файл version» ловится автоматически до тега.

**Non-Goals:**

- Отображение changelog на витрине: поле `history` в `store.yaml` остаётся в резерве, не заполняется.
- Смена способа чтения версии витриной — `releases/latest` устраивает.
- Приведение `registry.yaml` к полному перечню проектов — для витрины он полон по контракту.
- Автоматическая генерация changelog из git-истории: бэкфилл делается вручную один раз.
- Релиз-конвейер для `hours-bridge` (он не собирает артефакты в `dist/` и не публикует GitHub Releases).

## Decisions

### D1. Триггер бампа — релиз, а не порог и не команда

Бамп происходит только внутри `release.ps1`. Альтернативы отклонены: порог («N фич → версия») требует внедрения счётчика и моментов проверки, которых нет; команда владельца не автоматизируется и уже показала себя (номера бампаются по настроению, 634 сборки подряд). Релиз уже существует как событие, уже автоматизирован и уже разносится — вписываем бамп в него.

### D2. `versioning.yaml` в корне — отдельный файл, не расширение `registry.yaml`

`registry.yaml` — контракт витрины: каждая запись тянет валидацию `store.yaml`, скриншотов, иконки, релизов. Добавление туда `PersonalData` (приватные данные, контракта нет) и `TempProject` (нет git) сломало бы смысл реестра и добавило бы варнинги в сборку. Поэтому — второй файл с другим назначением: перечень проектов владельца и трек каждого.

Формат:

```yaml
projects:
  fogmap:
    repo: dziominpavel/FogMap
    track: release            # release | static
    version_file: version
    changelog: CHANGELOG.md
  benchmark:
    repo: dziominpavel/Benchmark
    track: static
    version_file: pyproject.toml
    changelog: CHANGELOG.md
  temp-project:
    track: static
    git: false                # без git — бамп и теги невозможны в принципе
    changelog: CHANGELOG.md
```

Альтернатива (расширить `registry.yaml` новой секцией `versioning:`) отклонена: два контракта с разной жизненной циклью в одном файле означают, что правка каталога витрины требует понимания версионирования, и наоборот.

### D3. Два трека, а не один общий

Статический трек (`Benchmark`, `PersonalData`, `TempProject`, витрина) не имеет `releases/latest`, значит версия для него — нечто внешнее (строка в `pyproject.toml` или отсутствие файла). Заставлять их гонять release-конвейер ради пустого тега — издержка без выгоды. Обязательным для обоих треков остаётся только `CHANGELOG.md`.

### D4. Правило живёт копией в каждом ребёнке, эталон — в корне

Агент, работающий в `C:\projects\GymProgress`, читает `AGENTS.md` и `docs/versioning.md` этого каталога. Глобального `AGENTS.md` в системе нет (проверено: ни в доме, ни в `C:\projects`). Ссылка из `AGENTS.md` ребёнка на репозиторий корня работала бы только при существующем локальном клоне и была бы хрупкой. Поэтому: полный текст эталона — `docs/versioning.md` корня; детям разносится копия, в шапке которой указано, что источник — корень.

Блок правил в `AGENTS.md` ребёнка — между маркерами:

```markdown
<!-- versioning:begin -->
## Версии и changelog (обязательно)
...5–8 строк: файл version не трогать вне релиза, пункт в [Unreleased]
при каждой пользовательской правке, бамп только release-скриптом...
<!-- versioning:end -->
```

Маркеры делают разнос идемпотентным: `sync` может обновить блок повторно, не затирая остальной текст `AGENTS.md` владельца. Альтернатива (переписывать весь `AGENTS.md` из шаблона) отклонена — в `AGENTS.md` детей уже лежат проектные правила (JDK-грабли FogMap, приоритеты ChargeForecast), их уничтожение недопустимо.

### D5. `versionCode` — счёт коммитов плюс база, а не починка формулы

Текущая формула не чинится: перенос разряда уже случился (`patch=634`), любой вариант «расширить разряды» ломает монотонность задним числом. Решение — схема FogMap, адаптированная к фактам:

```
versionCode = BASE + git rev-list --count HEAD
```

Базы (выше фактических текущих значений, ниже лимита Android 2 100 000 000):

| Проект | текущий `versionCode` | база | коммитов сейчас | станет |
|---|---|---|---|---|
| GymProgress | 2 000 010 634 | 2 000 100 000 | 58 | 2 000 100 058 |
| ChargeForecast | 2 000 000 131 | 2 000 100 000 | 8 | 2 000 100 008 |
| VoiceMind | 2 000 000 232 | 2 000 100 000 | 44 | 2 000 100 044 |
| Wishlot | 2 000 000 128 | 2 000 100 000 | 15 | 2 000 100 015 |

Одна общая база `2_000_100_000` для всех четырёх: она выше максимума (2 000 010 634) с запасом почти в 90 000 коммитов и оставляет ~99 900 000 до предела Android. Счёт коммитов растёт на каждой правке → установка отладочной сборки поверх старой всегда проходит. `versionName` при этом берётся из файла `version` и не зависит от сборки.

Альтернатива (оставить автобамп `VERSION_PATCH`, но не показывать его как `versionName`) отклонена: два числа с именем «версия» в одном проекте — ровно та путаница, из-за которой 634 сборки стали «версией 1.0.634», плюс `version.properties` остаётся файлом, который агенты трогают при каждой сборке, вместо того чтобы не трогать вообще.

### D6. Две фазы `release.ps1`: подготовка до сборки, публикация после

Бамп нельзя делать в момент публикации: ассеты и `versionName` запекаются при сборке, которая предшествует `release.ps1` (`build-apk.bat release` = Gradle → `dist/` → `release.bat`). Тег `vX.Y.Z` с APK, внутри которого `X.(Y-1).Z`, — та же проблема «версия ничего не значит», только со знаком минус. Поэтому бамп вынесен в фазу **подготовки**, выполняемую **до** сборки:

| Фаза | Команда | Что делает | Что не делает |
|---|---|---|---|
| Подготовка | `release.ps1 -Prepare` | отказ при пустом `[Unreleased]`, классификация, запись `version`, сворачивание секции, сверка форматов | тег, коммит, релиз |
| Публикация | `release.ps1` | отказ при непустом `[Unreleased]` и при нечистом дереве, коммит файлов бампа, сверка «верх секции == version», тег, push, релиз | бамп |

Почему коммит в публикации, а не в подготовке: если сборка упала, в репозитории не остаётся бамп-коммита без релиза — достаточно откатить два файла. К моменту публикации всё уже закоммичено владельцем, поэтому коммит содержит ровно два файла бампа и ложится поверх всей описанной в changelog работы; тег указывает на него и, через родителя, на неё целиком.

Обе фазы самопроверяемы: пустой `[Unreleased]` на подготовке → «нечего готовить»; непустой на публикации → «сначала подготовка». Перепутать порядок нельзя — отказ получит любая фаза.

Порядок последовательности для проектов без билд-скрипта (Android, zip/exe): `-Prepare` → сборка и копия в `dist/` → `release.ps1`. Для `FogMap` фаза подготовки вставлена в `build-apk.bat` при аргументе `release`, поэтому команда владельца не меняется.

### D6.1. Классификация по маркерам категорий секции

`release.ps1` парсит пункты `[Unreleased]` по маркерам категорий (в духе Keep a Changelog: `### Добавлено` → MINOR, `### Исправлено` → PATCH, `### Изменено` → MINOR, пометка `**BREAKING:**` → MAJOR) и берёт наивысший. MAJOR синтаксически из секции не выводится однозначно, поэтому владельцу доступен явный ключ `-Major`; по умолчанию автоматика решает сама. Если категории не распознаны, но пункты есть, — по умолчанию MINOR: никогда не утверждать «только фиксы», не зная наверняка; пропуск версии вперёд безопаснее, чем занижение уровня. Отказ происходит только при пустой секции.

### D7. `check-version.py` — обобщение fogmap-версии

Эталон из `FogMap/scripts/check-version.py` переносится с двумя правками: (1) подсказка по `git status` остаётся, но решение о NO_BUMP принимается не по патчам путей, а по наличию пункта в `[Unreleased]`; (2) читается путь из `versioning.yaml`, если файл присутствует (для прогона из корня по всем проектам). Проверка обязательна и как отдельная команда, и как шаг `release.ps1`.

### D8. Покатка — из корня, общим заходом

`sync-release.ps1` расширяется вторым набором файлов (`docs/versioning.md`, `scripts/check-version.py`, `CHANGELOG.md` скелет, блок `AGENTS.md` по маркерам) с тем же dry-run/`-Apply` и той же финальной сверкой. Так «всё в корне» означает не только место планирования, но и место исполнения: один запуск из корня обновляет детей, дети по-прежнему ничего не знают о соседях.

Сборка Android-правок (`build.gradle.kts`) и бэкфилл changelog'ов — задачи, которые разносом не сделать (свойские файлы проектов); они выполняются в детях, но по описанию из корнегого change и по эталону из корня.

## Risks / Trade-offs

- [Первый релиз после внедрения потребует классификации всей прошлой истории] → бэкфилл-уровень 2 делает `[Unreleased]` пустым на старте: версия не двигается до первого настоящего релиза, ничего классифицировать не нужно.
- [`sync`, пишущий через GitHub API, создаёт коммиты в детях без их ведома — а `AGENTS.md` FogMap требует явного разрешения на коммит] → разнос запускает владелец из корня как команду, коммит — часть этой команды; в задачах прописан показ diff перед `-Apply`.
- [`release.ps1` становится сложнее: две фазы, бамп, парсинг changelog, сверка, коммит] → $SCRIPT_VERSION поднимается, `sync-release.ps1` фиксирует расхождение копий и не даст смешать версии; логика подготовки изолирована в отдельный режим до существующих проверок.
- [Подготовленный, но неопубликованный релиз: `version` и `CHANGELOG.md` изменены, тега нет — выглядит как разъехавшееся состояние] → это нормальная пауза между фазами; откат = `git checkout -- version CHANGELOG.md`. Публикация откажется работать при непустом `[Unreleased]`, поэтому случайно опубликовать неподготовленное невозможно.
- [`versionCode` со счётчиком коммитов меняется при каждом коммите, а не только при релизе — сборка одинакова, а номер разный] → это осознанный обмен: Android требует строгого роста при каждой установке; отображаемая версия (`versionName`) от этого не страдает, витрина её не читает.
- [Общая база `2_000_100_000` для всех четырёх проектов — при будущем переносе базы правка в четырёх местах] → база вынесена в константу с комментарием-ссылкой на таблицу в design; смена базы — разовое событие, не циклическое.
- [`hours-bridge` остаётся без автоматического бампа — его спека требует бампа в коммите] → правка спеки `app-version` вынесена в задачи отдельным шагом, до неё правило и спека противоречат друг другу.
- [В 12 проектах появляется обязательный `CHANGELOG.md`, включая приватный `PersonalData`] → changelog описывает действия владельца с проектом, не данные; в задачах явно зафиксировано, что персональные данные в него не переносятся.

## Migration Plan

1. Корень: `versioning.yaml`, `docs/versioning.md`, `scripts/check-version.py`, правка `release.ps1` и `sync-release.ps1` — dry-run зелёный.
2. Дети релизного трека: `CHANGELOG.md` с бэкфиллом (сводная секция + секции существующих тегов), блок `AGENTS.md` по маркерам, копии эталонов.
3. Android-четвёрка: `build.gradle.kts` — снятие автобампа, `versionCode` по базе+счётчику, `versionName` из файла `version`; проверка `assembleDebug` + установка поверх старой сборки.
4. `hours-bridge`: `CHANGELOG.md`, переписанный раздел `AGENTS.md`, правка спеки `app-version`.
5. Статический трек: `CHANGELOG.md`, фиксация версии `Benchmark`.
6. Первый релиз любого проекта как контрольный прогон полного цикла.

Откат: правки детей обратимы git-ом; `release.ps1` со старой версии восстанавливается `sync-release.ps1` (эталон хранит предыдущие копии в git-истории корня). Сломанная монотонность `versionCode` не откатывается (Android не принимает понижение) — поэтому база берётся выше всех текущих значений с первого раза.

## Open Questions

- Нужен ли `PersonalData` файл `version` (сейчас решено: нет, changelog обязателен, версия статична и не хранится) — проявится при первой покатке, на спеки не влияет.
- Показывать ли потом changelog на странице приложения (поле `history`) — вне scope, спеки не меняет.
