# store-catalog Specification

## Purpose

Статическая витрина «Мои приложения»: сборка данных из контракта и GitHub API, структура и содержимое страниц, правила отображения скачиваний и автоматический деплой на GitHub Pages.

## Requirements

### Requirement: Автоматическая сборка витрины
Стор MUST собирать статику автоматически по трём независимым каналам: по событию (оповещение `repository_dispatch` от репозитория-источника — опубликованный GitHub-Release приложения либо коммит, тронувший web-статику), по расписанию (cron в GitHub Actions, период не более 30 минут — подстраховка) и при изменении `registry.yaml`. Событийный триггер MUST запускать сборку немедленно, без ожидания расписания; по этому же триггеру MUST выполняться деплой собранной статики. Сбой отправки или доставки оповещения MUST NOT оставлять витрину без обновления: ближайшая сборка по расписанию MUST подхватить изменения без участия владельца. На каждой сборке генератор (Python) MUST читать `registry.yaml`, `store.yaml` и скриншоты каждого проекта, а версию, размер, дату и ссылки на скачивание получать из GitHub API (`releases.latest`). Ручная сборка статики владельцем MUST NOT требоваться для обновления витрины.

#### Scenario: Опубликован новый релиз
- **WHEN** release-скрипт приложения публикует новый GitHub-Release и оповещает витрину
- **THEN** витрина пересобирается по этому оповещению, не дожидаясь cron, и показывает новую версию, размер и дату; ссылка «Скачать» ведёт на ассет нового релиза

#### Scenario: Оповещение о релизе не доехало
- **WHEN** релиз опубликован, но оповещение витрины не отправлено или потеряно (в том числе релиз, созданный минуя release-скрипт)
- **THEN** ближайшая сборка по расписанию показывает новый релиз, действий владельца сверх публикации MUST NOT требоваться

#### Scenario: Обновлена статика веб-приложения
- **WHEN** в репозитории-источнике веб-приложения пушится коммит, тронувший его статику, и источник оповещает витрину
- **THEN** витрина пересобирается по оповещению, не дожидаясь cron: страница `/apps/<slug>/` отдаёт новую статику, а дата web-карточки соответствует обновлению

#### Scenario: Изменено описание в store.yaml
- **WHEN** владелец правит `description` и пушит репозиторий приложения
- **THEN** витрина показывает новое описание после ближайшей синхронизации без каких-либо действий владельца, кроме push

### Requirement: Структура страниц
Витрина MUST состоять из: главной страницы (единая лента карточек — скачиваемые приложения и web-карточки вперемешку по убыванию даты + фильтр каталога с сегментами Все, Android, Windows, Web), отдельной страницы на каждое скачиваемое приложение (`/<slug>/`), страниц веб-приложений (`/apps/<slug>/`), страницы «О проекте». Язык витрины — только русский. Навигация между страницами MUST быть доступна с каждой страницы; шапка каждой страницы MUST содержать логотип витрины (ссылку на главную) рядом с названием сайта. Все карточки главной MUST идти в одной ленте по убыванию даты обновления (скачиваемые — по дате публикации релиза, web — по дате обновления данных); порядок записей в `registry.yaml` MUST определять только состав каталога, а не порядок карточек.

#### Scenario: Фильтр по платформе
- **WHEN** посетитель выбирает платформу Android на главной
- **THEN** отображаются только карточки приложений, у которых есть ассеты Android; web-карточки скрыты

#### Scenario: Сегмент Web
- **WHEN** посетитель выбирает сегмент Web на главной
- **THEN** в единой ленте отображаются только web-карточки, карточки скачиваемых приложений скрыты

#### Scenario: Страница приложения
- **WHEN** посетитель открывает `/<slug>/`
- **THEN** он видит: полное описание, обязательный блок системных требования (если задан), блок изменений последнего релиза («Что нового»), галерею скриншотов, версию, размер, дату, счётчик скачиваний, кнопки скачивания по каждой доступной платформе, ссылку «Исходники» на GitHub-репозиторий

#### Scenario: Страница веб-приложения
- **WHEN** посетитель открывает `/apps/<slug>/`
- **THEN** он видит веб-приложение и навигацию обратно в каталог; страница включена в sitemap

#### Scenario: Web-карточки в общей сетке
- **WHEN** в реестре есть записи секции `web:`
- **THEN** на главной странице в единой ленте среди карточек скачиваемых отображаются web-карточки по их дате обновления; они видны в сегментах Все и Web и скрыты в сегментах Android/Windows

#### Scenario: Порядок карточек
- **WHEN** приложения перечислены в `registry.yaml` в произвольном порядке, а даты их релизов и обновлений различаются
- **THEN** на главной все карточки идут от самой свежей даты к старой вперемешку, без группировки по типу; добавление новой записи в реестр MUST NOT менять порядок остальных карточек

### Requirement: Содержимое страницы «О проекте»
Страница «О проекте» MUST состоять из: лид-описания витрины, блока «Обо мне» с круглым фото автора и текстом о разработке приложений для личного использования, открытости проектов для пользователей и открытости автора к сотрудничеству (без указания имени) и раздела «Связаться» с прямыми ссылками на профили автора в Telegram, Instagram и LinkedIn. Фото MUST отображаться круглым, как в мессенджерах. Секции «Откуда данные» и «Почему всё так» MUST отсутствовать.

#### Scenario: Посетитель открывает «О проекте»
- **WHEN** посетитель открывает `/about/`
- **THEN** он видит блок «Обо мне» с круглым фото и текстом, а следом — раздел «Связаться» с тремя ссылками: Telegram, Instagram и LinkedIn

#### Scenario: Лишние секции не выводятся
- **WHEN** генератор рендерит страницу «О проекте»
- **THEN** секции «Откуда данные» и «Почему всё так» в разметке отсутствуют

### Requirement: Версия витрины на странице «О проекте»
Внизу страницы «О проекте» MUST отображаться версия витрины в формате `X.Y.Z` и ссылка на историю версий (GitHub Releases). Версия MUST читаться из файла `version`; при отсутствии или невалидном значении строка MUST NOT выводиться, а сборка MUST NOT падать. На главной и страницах приложений версия витрины MUST NOT отображаться.

#### Scenario: Версия есть
- **WHEN** файл `version` содержит `1.0.0`
- **THEN** внизу страницы «О проекте» после кнопки перехода в каталог отображается «Версия витрины: 1.0.0» и ссылка на историю версий

#### Scenario: Файл version недоступен
- **WHEN** файл `version` отсутствует или содержит не semver
- **THEN** строка версии не выводится, остальная страница собирается без ошибок

#### Scenario: Версия только на «О проекте»
- **WHEN** посетитель открывает главную или страницу приложения
- **THEN** версия витрины там не отображается

### Requirement: Карточка приложения
Карточка на главной MUST показывать: иконку (при отсутствии — цветная буквенная заглушка по первой букве названия), название, версию, размер, дату публикации релиза с явной подписью рядом с версией («v1.5.2 · 61.4 МБ · обновлено 23.09.2026»), кнопки скачивания по платформам. Счётчик скачиваний MUST отображаться на карточке и на странице приложения и MUST представлять собой сумму скачиваний по **всем опубликованным релизам** приложения — привязку к приложению, а не к последней версии; при этом в сумму MUST включаться все опубликованные релизы, в том числе prerelease, а draft-релизы MUST исключаться. Версия, размер, дата, ссылки на скачивание и блок «Что нового» остаются привязанными к последнему релизу. Дата MUST NOT дублироваться в строке счётчиков.

#### Scenario: Иконка отсутствует
- **WHEN** файл иконки проекта не найден
- **THEN** карточка и страница показывают буквенный плейсхолдер; витрина MUST NOT падать

#### Scenario: Дата на карточке
- **WHEN** генератор получает `published_at` последнего релиза из GitHub API
- **THEN** карточка показывает дату рядом с версией и размером с подписью, а строка счётчиков содержит только число скачиваний

#### Scenario: Счётчик скачиваний
- **WHEN** генератор получает `download_count` ассетов всех опубликованных релизов приложения из GitHub API
- **THEN** на карточке и странице приложения отображается сумма этих скачиваний

#### Scenario: Счётчик не обнуляется при новой версии
- **WHEN** опубликован новый релиз приложения, чьи ассеты ещё не скачивали, а предыдущие релизы скачивали суммарно 500 раз
- **THEN** после ближайшей синхронизации счётчик показывает 500 (плюс скачивания нового релиза), а не 0

#### Scenario: Prerelease и draft в сумме
- **WHEN** у приложения есть обычный релиз (100 скачиваний), prerelease (30 скачиваний) и draft (50 скачиваний)
- **THEN** счётчик показывает 130: prerelease включён, draft исключён

### Requirement: Производные изображения вместо исходников
Витрина MUST публиковать скриншоты и иконки только в виде оптимизированных производных WebP, а исходные файлы из репозиториев приложений MUST NOT попадать в выходной каталог сборки. Для каждого скриншота MUST создаваться варианты шириной 540 и 1080 px с сохранением пропорций; для каждой иконки — варианты 96 и 192 px. Исходное изображение MUST NOT увеличиваться сверх своих размеров.

#### Scenario: Скриншот публикуется производными
- **WHEN** в репозитории приложения лежит исходный скриншот 1080×2400
- **THEN** в выходном каталоге для него есть WebP-варианты 540 и 1080 px по ширине, а исходный файл отсутствует

#### Scenario: Иконка публикуется производными
- **WHEN** в репозитории приложения лежит иконка 512×512
- **THEN** в выходном каталоге для неё есть WebP-варианты 96 и 192 px, а исходный файл иконки отсутствует

#### Scenario: Исходник меньше целевой ширины
- **WHEN** исходный скриншот уже 1080 px
- **THEN** вариант 1080 px не увеличивается сверх исходной ширины и сохраняет пропорции

### Requirement: Адаптивная разметка галереи
Галерея скриншотов MUST ссылаться на производные через `srcset` с кандидатами 540w и 1080w и атрибут `sizes`, соответствующий сетке галереи. Каждое изображение MUST иметь явные `width` и `height`, `loading="lazy"` и `decoding="async"`. Ссылка открытия скриншота MUST вести на вариант 1080 px, а не на исходный файл.

#### Scenario: Браузер выбирает подходящий вариант
- **WHEN** посетитель открывает страницу приложения с галереей
- **THEN** разметка изображения содержит `srcset` с 540w и 1080w, `sizes`, `width`, `height`, `loading="lazy"` и `decoding="async"`

#### Scenario: Открытие скриншота
- **WHEN** посетитель нажимает на скриншот в галерее
- **THEN** открывается WebP-вариант шириной 1080 px, а не исходный PNG

#### Scenario: Пропорции не искажаются
- **WHEN** браузер отрисовывает изображение с заданными `width` и `height` в ячейке другого размера
- **THEN** изображение сохраняет исходные пропорции без растягивания

### Requirement: Разметка иконок приложений
Иконки на карточке главной и на странице приложения MUST отдаваться через `srcset` с вариантами 96w и 192w и атрибутом `sizes`, соответствующим месту показа (56 px на карточке, 96 px на странице). При отсутствии файла иконки MUST отображаться буквенный плейсхолдер, а сборка MUST NOT падать.

#### Scenario: Иконка на карточке и странице
- **WHEN** у приложения есть иконка
- **THEN** карточка и страница используют `srcset` с 96w и 192w, а `sizes` равен 56 px на карточке и 96 px на странице

#### Scenario: Иконка отсутствует
- **WHEN** файл иконки не найден
- **THEN** отображается буквенный плейсхолдер, изображение иконки не выводится

### Requirement: Устойчивость к битым изображениям
Если исходный скриншот или иконка не читается или не кодируется, сборка MUST NOT падать. Битый скриншот MUST пропускаться с предупреждением в лог, остальные изображения и страница MUST оставаться доступными; битая иконка MUST приводить к буквенному плейсхолдеру.

#### Scenario: Битый скриншот
- **WHEN** один из скриншотов приложения повреждён
- **THEN** сборка завершается успешно, в лог выводится предупреждение, остальные скриншоты публикуются

#### Scenario: Битая иконка
- **WHEN** файл иконки повреждён
- **THEN** сборка завершается успешно, на карточке и странице показывается буквенный плейсхолдер

### Requirement: Блок «Превью» при отсутствии скриншотов
Если у приложения нет ни одного подготовленного скриншота, страница MUST показывать в месте галереи секцию «Превью» с текстовым сообщением о том, что скриншоты появятся позже. Блок MUST NOT содержать изображений и фейковых скриншотов. При наличии хотя бы одного подготовленного скриншота MUST показываться галерея с реальными изображениями без добивки до трёх.

#### Scenario: Нет ни одного скриншота
- **WHEN** у приложения нет исходных скриншотов
- **THEN** страница показывает секцию «Превью» с текстом, а в секции нет тега `<img>` и фейковых изображений

#### Scenario: Один или два скриншота
- **WHEN** у приложения подготовлен один или два скриншота
- **THEN** страница показывает галерею только с этими изображениями, блок «Превью» отсутствует

#### Scenario: Все изображения не удалось подготовить
- **WHEN** исходные скриншоты есть, но ни один не удалось преобразовать в превью
- **THEN** страница показывает блок «Превью», а не пустую галерею

#### Scenario: Оформление в обеих темах
- **WHEN** посетитель переключает тёмную или светлую тему
- **THEN** блок «Превью» использует цвета темы витрины и не требует загрузки изображений

### Requirement: Кнопки скачивания и авто-детект платформ
Кнопки скачивания формируются по ассетам релиза: `*.apk` → Android, `*-win*.zip`/`*.exe` → Windows. Поле `platforms` в `store.yaml` MUST отсутствовать (авто-детект). Если у одной платформы несколько подходящих ассетов, MUST отображаться все как варианты с указанием имени и размера. Каждая кнопка MUST вести напрямую на URL ассета релиза.

#### Scenario: Один ассет на платформу
- **WHEN** в релизе один `*.apk`
- **THEN** показывается одна кнопка Android со ссылкой на этот ассет

#### Scenario: Несколько ассетов одной платформы
- **WHEN** в релизе два подходящих ассета одной платформы
- **THEN** показываются оба варианта с именами и размерами; оба доступны для скачивания

#### Scenario: Неизвестный тип ассета
- **WHEN** ассет не подходит ни под одну маску платформы
- **THEN** он не показывается на витрине, но не блокирует показ остальных ассетов

### Requirement: Подсказка для неподписанных Windows-приложений
На страницах Windows-приложений (zip, exe) MUST присутствовать подсказка о том, что файл не подписан сертификатом и Windows/антивирус может показывать предупреждение при первом запуске, с указанием, что код открыт и его можно проверить.

#### Scenario: Посетитель скачивает exe
- **WHEN** посетитель открывает страницу приложения с Windows-ассетом
- **THEN** рядом с кнопкой скачивания видна подсказка о возможном предупреждении SmartScreen/антивируса

### Requirement: Оформление и аналитика
Витрина MUST работать в тёмной теме по умолчанию (dark-first) с переключателем ровно двух режимов — тёмная/светлая, без системного режима; переключатель MUST отображаться круглой кнопкой-иконкой (солнце или луна). Выбор темы MUST сохраняться между посещениями и применяться без перезагрузки страницы; при первом визите, при отсутствии сохранённого выбора и при сохранённом значении, не являющемся `dark` или `light` (включая устаревшее `system`), MUST применяться тёмная тема, а на загруженной странице MUST отсутствовать вспышка светлой темы. MUST использоваться буквенный auto-favicon. Витрина MUST включать счётчик посещений GoatCounter (одна строка в шаблоне); MUST генерироваться sitemap и meta-теги. Адрес витрины — `dziominpavel.github.io`, деплой — GitHub Pages из CI без ручных действий.

#### Scenario: Первый визит
- **WHEN** посетитель открывает витрину впервые
- **THEN** отображается тёмная тема, страница работает без cookie-баннера и без вспышки светлой темы

#### Scenario: Смена темы
- **WHEN** посетитель нажимает кнопку-иконку переключателя и позже возвращается на витрину
- **THEN** тема переключается мгновенно без перезагрузки страницы, выбранная тема сохраняется при следующем визите

#### Scenario: Устаревшее значение темы
- **WHEN** в localStorage сохранено значение `system` (от прежней трёхрежимной версии) или иное недопустимое значение
- **THEN** применяется тёмная тема, переключатель работает только в режимах тёмная/светлая

### Requirement: Главная страница: hero и фильтр со счётчиками
Главная страница MUST показывать вступительный блок (hero): заголовок витрины рядом с иконкой-логотипом, подзаголовок (lead) и сегментированный фильтр по платформам, размещённый в hero. Lead MUST коротко позиционировать витрину как бесплатный каталог приложений для Android, Windows и веб, доступных для скачивания, и MUST NOT упоминать регистрацию, условия доступа и внутренние детали инфраструктуры (источник данных, GitHub Releases). Разбивка каталога по платформам и итоговое число карточек MUST выводиться ровно один раз — счётчиками сегментов фильтра; отдельная полоса статистики в hero MUST отсутствовать. Счётчик сегмента «Все» MUST равняться числу всех карточек каталога (скачиваемые и web), счётчики платформенных сегментов — числу карточек этой платформы, и оба MUST быть синхронны с `registry.yaml`. Активный сегмент MUST визуально выделяться.

#### Scenario: Счётчики фильтра
- **WHEN** генератор знает о 9 приложениях (7 скачиваемых: 5 Android и 2 Windows, плюс 2 web)
- **THEN** фильтр показывает «Все 9», «Android 5», «Windows 2», «Web 2», а полоса статистики в hero отсутствует

#### Scenario: Веб-приложений нет
- **WHEN** в секции `web:` реестра нет записей
- **THEN** сегмент Web в фильтре отсутствует, а счётчик «Все» равен числу скачиваемых приложений

#### Scenario: Выбор сегмента
- **WHEN** посетитель видит главную страницу и выбирает сегмент фильтра
- **THEN** после выбора отображаются только карточки выбранной платформы (для сегмента Web — web-карточки), а счётчик сегмента показывает число подходящих карточек

#### Scenario: Подзаголовок hero
- **WHEN** посетитель открывает главную страницу
- **THEN** под заголовком «Мои приложения» виден lead «Каталог бесплатных приложений: Android, Windows и веб. Скачивайте готовые сборки.» — без упоминания регистрации, условий доступа и источника данных

#### Scenario: Логотип на главной
- **WHEN** посетитель открывает главную страницу
- **THEN** рядом с заголовком отображается круглая иконка-логотип витрины, а в шапке страницы — та же иконка рядом с названием сайта

### Requirement: Волна появления карточек (стаггер)
Карточки главной MUST появляться волной: каждая следующая выезжает через фиксированный шаг 45 мс после предыдущей, а порядок волны MUST совпадать с порядком карточек в (отфильтрованной) сетке. Волна MUST запускаться при первой загрузке страницы и при каждом переключении сегмента фильтра и в обоих случаях MUST выглядеть одинаково. При `prefers-reduced-motion` действует требование «Доступность оформления и анимации»: появление мгновенное, без волны.

#### Scenario: Первая загрузка
- **WHEN** посетитель открывает главную страницу
- **THEN** все карточки выезжают по очереди с шагом 45 мс в порядке сетки

#### Scenario: Сегмент с меньшим числом карточек
- **WHEN** посетитель выбирает сегмент Android, где видна только часть карточек
- **THEN** волна идёт по видимым карточкам с тем же шагом 45 мс и MUST NOT ждать невидимых соседей

### Requirement: Перезапуск волны при переключении фильтра
При каждом переключении сегмента фильтра волна MUST проигрываться заново для всех видимых карточек: волна от предыдущей загрузки или прошлого клика MUST NOT идти параллельно с новой, и карточка MUST NOT выезжать вне порядка сетки. Задержка каждой видимой карточки MUST пересчитываться при каждом переключении — устаревшие задержки MUST NOT сохраняться.

#### Scenario: Возврат к «Все» до конца предыдущей волны
- **WHEN** посетитель выбирает сегмент Android и возвращается к сегменту Все, не дожидаясь окончания предыдущей волны
- **THEN** все видимые карточки заново выезжают волной строго в порядке сетки: нижняя по позиции карточка MUST NOT начать выезжать раньше верхней

#### Scenario: Повторные переключения подряд
- **WHEN** посетитель несколько раз подряд переключает сегменты фильтра
- **THEN** каждое переключение запускает новую волну по видимым карточкам, задержки которых соответствуют их текущему порядку в сетке

### Requirement: Доступность оформления и анимации
Оформление витрины MUST поддерживать видимый индикатор фокуса при навигации с клавиатуры (`:focus-visible`) и MUST учитывать настройку `prefers-reduced-motion`: анимации переключения темы и появления элементов при этой настройке MUST быть отключены или мгновенными. Контраст основного текста и подписей MUST соответствовать уровню WCAG AA (4.5:1) в обеих темах.

#### Scenario: Клавиатурная навигация
- **WHEN** посетитель переходит клавишей Tab к кнопке, ссылке или сегменту фильтра
- **THEN** элемент показывает видимое кольцо фокуса

#### Scenario: Система просит уменьшить анимацию
- **WHEN** в операционной системе включено `prefers-reduced-motion`
- **THEN** переключение темы и появление карточек происходят без анимации (мгновенно)

### Requirement: Блок «Что нового» на странице приложения
Страница скачиваемого приложения MUST показывать секцию изменений последнего релиза — краткий пользовательский блок, опубликованный телом GitHub-Release. Источник текста — поле `body` последнего релиза, получаемого из того же ответа GitHub API, что и версия, размер и ассеты; отдельных запросов к API ради секции MUST NOT добавляться. Секция MUST размещаться в основном потоке страницы после описания и системных требований и перед галереей скриншотов и сопровождаться заголовком с версией релиза и ссылкой «Все изменения» на страницу релизов репозитория.

Содержимое тела релиза MUST рендериться по его реальному формату: строка-жирная метка категории (`**Добавлено**` и аналоги) — заголовком блока, буллет (`- ...`) — элементом списка, прочие строки (свободная проза исторических релизов) — абзацами. Весь текст MUST экранироваться: тело релиза — данные внешнего источника, и его разметка MUST отображаться как текст, а не исполняться. Секция MUST обновляться наравне с версией и размером — ближайшей сборкой витрины после публикации релиза.

Если тело релиза пустое (или состоит только из пробельных символов), секция MUST отсутствовать на странице, а сама страница MUST рендериться без изменений и без предупреждений. Секция MUST выводиться только на страницах скачиваемых приложений; карточки главной страницы и страницы веб-приложений (`/apps/<slug>/`) оставаться без неё.

#### Scenario: Тело релиза с метками и буллетами
- **WHEN** тело последнего релиза состоит из жирных меток категорий и буллетов
- **THEN** страница приложения показывает секцию «Что нового» с версией релиза: метки выводятся заголовками соответствующих блоков, буллеты — списком, рядом есть ссылка «Все изменения» на страницу релизов репозитория

#### Scenario: Старый релиз со свободной прозой
- **WHEN** тело последнего релиза (опубликованное до введения формат-контракта) состоит из связных строк без меток и буллетов
- **THEN** текст выводится абзацами без списков, страница рендерится без ошибок

#### Scenario: Пустое тело релиза
- **WHEN** у последнего релиза нет текста тела или оно состоит только из пробельных символов
- **THEN** секция «Что нового» на странице отсутствует, остальное содержимое страницы не меняется

#### Scenario: Спецсимволы в теле релиза
- **WHEN** тело релиза содержит символы разметки (`<`, `&`, `"`), жирные метки и буллеты одновременно
- **THEN** все символы выводятся как видимый текст, разметка страницы не нарушается, XSS через тело релиза невозможен

#### Scenario: Web-приложение и карточка главной
- **WHEN** генератор рендерит страницу веб-приложения `/apps/<slug>/` и карточки главной
- **THEN** секция «Что нового» в их разметке отсутствует

### Requirement: Отсутствие горизонтальной прокрутки на мобильных экранах

На ширине вьюпорта от 360 до 430 CSS px каждая страница витрины MUST
укладываться в ширину экрана: ширина содержимого документа MUST NOT превышать
ширину вьюпорта, горизонтальная прокрутка страницы MUST отсутствовать.
Локальная прокрутка внутри отдельного блока MAY сохраняться, если она не
расширяет страницу.

#### Scenario: Главная страница на 360 px
- **WHEN** посетитель открывает главную страницу при ширине вьюпорта 360 px
- **THEN** ширина содержимого документа не превышает ширину вьюпорта, а hero, фильтр и карточки целиком помещаются по ширине

#### Scenario: Страница приложения на 390 px
- **WHEN** посетитель открывает страницу приложения с длинным названием и описанием при ширине вьюпорта 390 px
- **THEN** страница не прокручивается по горизонтали, а длинные строки переносятся внутри своих блоков

### Requirement: Компактная шапка на мобильных экранах

На ширине вьюпорта до 480 CSS px шапка витрины MUST показывать логотип,
название сайта, ссылки навигации и переключатель темы в одной строке без
переноса. Высота шапки MUST NOT превышать 64 px, а сама шапка MUST оставаться
закреплённой при прокрутке страницы.

#### Scenario: Шапка на 360 px
- **WHEN** посетитель открывает любую страницу витрины при ширине вьюпорта 360 px
- **THEN** логотип, название сайта, ссылки «Главная» и «О проекте» и переключатель темы стоят в одной строке, а высота шапки не превышает 64 px

#### Scenario: Прокрутка длинной страницы
- **WHEN** посетитель прокручивает страницу приложения вниз
- **THEN** шапка остаётся видимой в верхней части экрана

### Requirement: Фильтр каталога на мобильных экранах

На ширине вьюпорта до 600 CSS px сегменты фильтра MUST располагаться сеткой
ровно в две колонки. При нечётном числе сегментов последний MUST занимать всю
ширину строки; при чётном числе ни один сегмент MUST NOT оставаться
единственным в своей строке. Счётчик сегмента MUST оставаться на одной строке
с названием сегмента.

#### Scenario: Четыре сегмента на 360 px
- **WHEN** на главной доступны сегменты «Все», «Android», «Windows» и «Web»
- **THEN** при ширине вьюпорта 360 px сегменты образуют две строки по два, а счётчик каждого сегмента стоит рядом с его названием

#### Scenario: Веб-приложений нет
- **WHEN** сегмент «Web» отсутствует и остаются три сегмента
- **THEN** первые два стоят в одной строке, а третий занимает всю ширину следующей строки

### Requirement: Галерея скриншотов на мобильных экранах

При ширине вьюпорта от 360 до 480 CSS px галерея скриншотов MUST показывать не
менее двух колонок. Изображения MUST сохранять пропорции и MUST NOT выходить за
границы своей колонки.

#### Scenario: Галерея на 360 px
- **WHEN** посетитель открывает страницу приложения с галереей при ширине вьюпорта 360 px
- **THEN** скриншоты идут не менее чем в две колонки, а каждый снимок целиком помещается в свою колонку

### Requirement: Блок скачивания на странице приложения

На странице скачиваемого приложения блок скачивания MUST отображаться сразу
после заголовка приложения (иконка, название, версия, размер, дата, счётчик
скачиваний) и ДО описания, системных требований, «Что нового» и галереи. При
ширине вьюпорта от 1024 px блок MUST оставаться в правой колонке страницы.

#### Scenario: Мобильный порядок блоков
- **WHEN** посетитель открывает страницу приложения при ширине вьюпорта 360 px
- **THEN** блок «Скачать» виден после заголовка приложения и раньше описания, требований, «Что нового» и галереи

#### Scenario: Широкая раскладка
- **WHEN** посетитель открывает страницу приложения при ширине вьюпорта 1280 px
- **THEN** блок «Скачать» стоит в правой колонке, а описание, требования, «Что нового» и галерея — в левой

### Requirement: Область нажатия на мобильных экранах

На ширине вьюпорта до 600 CSS px каждый интерактивный элемент витрины —
ссылки навигации, сегменты фильтра, переключатель темы, кнопки скачивания и
ссылки «Исходники» — MUST иметь область нажатия не менее 44×44 CSS px.

#### Scenario: Кнопки скачивания
- **WHEN** посетитель открывает страницу приложения при ширине вьюпорта 360 px
- **THEN** высота каждой кнопки скачивания не меньше 44 px

#### Scenario: Сегменты фильтра
- **WHEN** посетитель открывает главную страницу при ширине вьюпорта 360 px
- **THEN** высота каждого сегмента фильтра не меньше 44 px
