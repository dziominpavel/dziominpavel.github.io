# versioning-policy Specification

## Purpose

Единая политика версии и changelog для всех проектов владельца: что такое версия, когда она меняется, как копятся изменения между релизами и почему дети-проекты не знают друг о друге.

## Requirements

### Requirement: Источник истины версии — файл version
В релизном треке единственный источником базы версии MUST быть файл `version` в корне проекта (формат `MAJOR.MINOR.PATCH`, одна ASCII-строка). Номер версии приложения MUST NOT вычисляться из счётчика сборок, счёта коммитов или иного изменяемого при каждой сборке значения. Файл `version` MUST меняться только в момент релиза.

#### Scenario: Обычная сессия без релиза
- **WHEN** в проект выполнена серия изменений кода без запуска релиза
- **THEN** файл `version` остаётся неизменным, а изменения отражены в секции `## [Unreleased]` файла `CHANGELOG.md`

#### Scenario: Релиз меняет версию
- **WHEN** выпущен релиз с накопленными изменениями
- **THEN** файл `version` содержит новый номер, отличный от предыдущего релиза

### Requirement: Изменения копятся в секции Unreleased
Между релизами в changelog попадают **только глобальные доработки** — новая функция, заметное изменение поведения, фикс, который пользователь реально видит. Такая доработка MUST быть записана в секцию `## [Unreleased]` файла `CHANGELOG.md` в момент выполнения работы, а не откладываться до релиза. Секция `[Unreleased]` MUST существовать всегда и MUST NOT иметь номера версии. Мелкие правки без заметного эффекта для пользователя MUST NOT добавляться в changelog: косметика UI (отступы, цвета, выравнивание, подпись элемента) и локальные улучшения, которых пользователь не заметит, как и чистые доки, спеки, тесты, чистый рефактор и CI.

#### Scenario: Накопление нескольких фич в одну версию
- **WHEN** между релизами внесено несколько независимых глобальных доработок
- **THEN** все они перечислены в одной секции `[Unreleased]` и при следующем релизе образуют одну версию

#### Scenario: Изменение без пользовательского эффекта
- **WHEN** выполнена только правка документации или спеки
- **THEN** секция `[Unreleased]` не пополняется

#### Scenario: Мелкая правка интерфейса
- **WHEN** поправлена косметика элемента — отступ, цвет, выравнивание или подпись — без изменения функциональности
- **THEN** секция `[Unreleased]` не пополняется

### Requirement: Changelog обязателен в каждом проекте
Каждый проект владельца MUST содержать файл `CHANGELOG.md` в корне. Changelog MUST вести историю на русском языке и MUST содержать сверху секцию `## [Unreleased]`, а ниже — выпущенные версии в формате `## [X.Y.Z] — дата (УРОВЕНЬ)`. Первичное заполнение MUST покрывать прошлое истории проекта сводной секцией и секциями на существующие теги; сборочные номера, не бывшие релизами, в changelog MUST NOT перечисляться.

#### Scenario: Проект без changelog
- **WHEN** у проекта из перечня владельца отсутствует `CHANGELOG.md`
- **THEN** это считается нарушением политики и устраняется при ближайшей покатке

#### Scenario: История без тегов
- **WHEN** у проекта есть коммиты, но теги отсутствуют
- **THEN** прошлое отражается одной сводной секцией, а не попунктной реконструкцией каждой сборки

### Requirement: Бамп версии только на релизе
Повышение версии MUST происходить исключительно как часть публикации релиза. Промежуточная версия — версия, не ставшая git-тегом и GitHub-Release, — MUST NOT существовать: между релизами номер версии MUST оставаться номером последнего релиза.

#### Scenario: Несколько сессий между релизами
- **WHEN** прошло несколько сессий работы с десятками коммитов
- **THEN** выпущен ровно одна новая версия, объединяющая всё накопленное

#### Scenario: Попытка бампа вне релиза
- **WHEN** версия повышена без публикации релиза
- **THEN** это нарушает политику; следующий выпуск обязан опираться на накопленные в changelog изменения, а не на внезапно изменившийся номер

### Requirement: Классификация уровня при релизе
Уровень новой версии MUST определяться по всему накопленному содержимому секции `[Unreleased]` и браться по наивысшему применимому уровню: наличие ломающего изменения — MAJOR, наличие новой функции или поведения — MINOR, только исправления — PATCH. В одной версии MUST размещаться несколько накопленных изменений; отдельная версия на каждое изменение MUST NOT выпускаться.

#### Scenario: Фичи и фиксы вместе
- **WHEN** в `[Unreleased]` накоплены новая функция и несколько исправлений
- **THEN** выпускается одна версия уровня MINOR, содержащая и то, и другое

#### Scenario: Только исправления
- **WHEN** в `[Unreleased]` только исправления
- **THEN** выпускается версия уровня PATCH

### Requirement: Два трека проектов
Каждый проект MUST относиться к одному из двух треков. Релизный трек: проект выходит релизом и его версия растёт по описанным правилам. Статический трек: проект не выпускает релизов, его версия MUST оставаться замороженной (в том числе фиксированной строкой в манифесте проекта), при этом `CHANGELOG.md` с секцией `[Unreleased]` остаётся обязательным.

#### Scenario: Статический проект
- **WHEN** проект статического трека (например, репозиторий-витрина или модельный бенчмарк) получает изменения
- **THEN** `CHANGELOG.md` пополняется, а версия остаётся неизменной и не публикуется как релиз

#### Scenario: Проект статического трека переходит в релизный
- **WHEN** проект получает release-конвейер и публикует первый релиз
- **THEN** он начинает соблюдать релизные правила с этого момента, changelog сохраняет прошлую историю

### Requirement: Android-версия отделена от счётчика сборок
В Android-проектах отображаемая версия приложения (`versionName`) MUST браться из файла `version`, а внутренний номер сборки (`versionCode`) MUST расти монотонно и MUST NOT зависеть от классификации версии. Расчёт `versionCode` MUST гарантировать, что для любого следующего релиза значение выше предыдущего; автобамп номера при каждой Gradle-сборке MUST отсутствовать.

#### Scenario: Первый бамп после внедрения
- **WHEN** проект с историческим `versionCode` выше нового базового значения выпускает релиз с повышенной версией
- **THEN** новый `versionCode` строго больше предыдущего, обновление устанавливается без отказа «понижение версии»

#### Scenario: Сборка без релиза
- **WHEN** выполняется обычная отладочная сборка
- **THEN** ни файл `version`, ни отображаемая версия приложения не меняются

### Requirement: Распределение знаний между корнем и детьми
Единственным местом, хранящим перечень всех проектов владельца и трек каждого из них, MUST быть корневой репозиторий (файл `versioning.yaml`). Дочерний проект MUST знать только собственные файлы версии и changelog и MUST NOT содержать знаний о других проектах владельца — ни списка репозиториев, ни их треков, ни их версий. Эталон правила и эталон проверки MUST жить в корне и MUST доставляться детям как копии собственных им файлов.

#### Scenario: Дети получают только своё
- **WHEN** корень выполняет разнос файлов по проектам
- **THEN** каждый проект получает только собственные `CHANGELOG.md`, `docs/versioning.md`, `scripts/check-version.py` и блок правил; файлы, описывающие другие проекты, не передаются

#### Scenario: Новый проект
- **WHEN** владелец добавляет новый репозиторий
- **THEN** он описывается одной записью в `versioning.yaml` корня без правок дочерних проектов

### Requirement: Проверка рассинхрона версии и changelog
Для релизного трека MUST существовать автоматическая проверка, сверяющая формат файла `version` с верхней секцией `CHANGELOG.md`. При рассинхроне (верхняя секция не совпадает с файлом `version`) проверка MUST завершаться ошибкой. Проверка MUST быть доступна локально и MUST выполняться перед публикацией релиза.

#### Scenario: Версия и changelog совпадают
- **WHEN** файл `version` равен верхней версионной секции changelog
- **THEN** проверка завершается с кодом 0

#### Scenario: Changelog отстал от версии
- **WHEN** файл `version` содержит `1.6.0`, а верхняя секция changelog — `## [1.5.2]`
- **THEN** проверка завершается ненулевым кодом с указанием рассинхрона
